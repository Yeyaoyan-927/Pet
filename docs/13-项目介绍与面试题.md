# PawPilot（PetGroom）项目介绍与面试题

> 用途：面试前快速回顾项目、准备技术问答。所有内容均对照真实代码，可在 `backend/`、`frontend/` 中复现。
> 共 34 题：A~F 六大方向，标 ★ 的是细分追问（面试官深挖时常问）。

---

## 一、项目简介

**PawPilot（内部代号 PetGroom）** 是一套面向宠物洗护 / 寄养门店的一站式经营 SaaS。核心特性是把「门店日常经营」和「多 Agent 智能体」结合：宠主自助预约、店员现场运营、店长经营分析，三端共享同一套业务数据、同一套 Agent 定义与同一个执行内核。

- **定位**：单体进程 + 本地数据库的门店私有化部署（非 SaaS 多租户），强调「规则保证正确性，AI 只提效」。
- **当前版本**：V8.6.0（截至 2026-10）。
- **最大亮点**：路由调度 Agent 分派 + 7 个领域子 Agent 执行 + 合规风控 Agent 兜底，共 9 个 Agent；业务闭环用有限状态机保证正确性；写操作绝不交给 LLM 直跑，必须经业务服务层做权限 → 状态机 → 事务 → 审计。
- **RAG 口径**：知识库是全部 Agent 的统一底座，检索在**对话链路内**由 Agent 自主触发，知识库页面只做文档治理，不设独立搜索入口。

## 二、技术栈

| 层        | 选型                                                                              |
| -------- | ------------------------------------------------------------------------------- |
| 后端       | Python 3.13 + FastAPI + SQLAlchemy 2.x（async）+ aiomysql + Alembic + Pydantic v2 |
| 数据库      | MySQL 8（`pet_groom`）                                                            |
| 前端       | Vue 3 + Vite + TypeScript + Element Plus + Pinia + ECharts                      |
| LLM      | 阿里云百炼 OpenAI 兼容模式，用 `httpx` 直连，**不引入 openai SDK**，型号可配置、零硬编码                    |
| Agent    | 多 Agent 协作：路由调度 + 6 领域子 Agent + 合规风控；自研 ReAct 执行内核，**不引入 CrewAI / AutoGen**       |
| 向量 / RAG | Chroma 本地持久化 + LlamaIndex；embedding 走百炼 `text-embedding-v4`                     |
| 鉴权       | JWT + RBAC（宠主 / 店员 / 店长三角色）                                                     |

### 代码结构（RAG 在哪）

```
backend/app/
├── rag/                     # ★ RAG 能力包：只放可复用组件，不碰事务与权限
│   ├── index.py             #   Chroma + LlamaIndex 向量索引（embedding 三级降级、空间隔离）
│   └── parser.py            #   PDF / Word / TXT / MD 解析 + 三种切块策略（页码 / 段落 / 字符区间）
├── services/
│   ├── knowledge_service.py         # 检索编排、索引新鲜度校验
│   └── knowledge_ingest_service.py  # 上传 → 解析 → 切块 → 入库的异步任务编排
├── routers/knowledge.py     # 10 个接口 + 权限守卫（店员 / 店长）
├── models/knowledge.py      # 4 张表：知识条目 / 上传文档 / 文本块 / 入库任务
└── schemas/knowledge.py     # 切块参数校验（块大小、重叠长度）
```

一句话记法：**能力在 `app/rag`，编排在 `app/services`**。向量库换实现不影响业务层，业务层换流程也不影响索引。

## 三、架构关键设计（面试常问的「为什么」）

1. **9 个 Agent 分工 + 一套执行内核**：路由调度 Agent 判意图派活，健康问诊 / 饲养营养 / 行为训练 / 用品导购 / 宠物档案 / 门店业务 / 经营分析七个领域 Agent 执行，合规风控 Agent 横切。它们共用同一个 ReAct 执行器和工具注册表，本质是「一套内核 + 九份领域配置」——子 Agent 只带自己的领域提示词与工具子集，规则互不稀释。
2. **三端激活组合**：`ROLE_TOOL_PROFILE` 把工具池按端收敛成不同白名单——宠主 13 个、店员 11 个、店长 11 个（池 30 个）。端与端的差别不只是工具，还包括哪些 Agent 能激活：健康问诊对宠主完整开放、店员仅预问诊辅助、店长只看风险报告。
3. **ReAct 内循环 + 有限状态机（Graph Workflow）外骨架**：意图识别 / 工具调用走 ReAct 思维-行动循环；真正的业务闭环（预约状态流转、寄养生命周期等）用状态机保证正确性，不让模型自由发挥。
4. **写操作强制走服务层**：Agent 只负责「意图识别 + 参数收集」，真正落库由 `app/services/*` 执行，内含权限校验、状态机推进、事务、`operation_log` 审计。
5. **确定性动作规则优先**：跳转页面、开关摄像头这类动作直接由规则触发，不让 LLM 改判，避免幻觉。
6. **可降级**：LLM 不可用、embedding 失败、检索为空都有兜底（模板摘要、标签兜底、返回空但给提示），绝不返回空响应当作「没话说」。

## 四、面试题与参考答案

### A. 架构与 Agent 设计

**Q1. 为什么拆成多 Agent？拆了为什么又不用 CrewAI / AutoGen？**

> **先说为什么拆**：三个领域对提示词的要求是互相冲突的——健康问诊的红线是「不诊断、不开处方」，
> 用品导购要贴着库存和价格说话，档案 Agent 要读写长期记忆。把这套塞进同一个决策点，
> 个别领域的规则会被稀释；拆开之后每个子 Agent 只带自己的领域提示词和工具子集，规则不打架。
> **再说为什么不用框架**：CrewAI / AutoGen 的默认玩法是让 Agent 之间自由对话协商，
> 流程不可预测、责任边界模糊、写操作越权风险放大，出了事查不清是哪个 Agent 决定的。
> 我的做法是**自研编排**：路由 Agent 按写死的规则分派（健康判断永远先于营养建议，有依赖串行、
> 无依赖并行），子 Agent 之间不直接对话，上下文由路由层显式传递。
> **还要说清「多」在哪**：9 个 Agent 不是 9 个进程、也不是 9 个模型实例，它们共用同一个 ReAct
> 执行器与工具注册表，本质是「一套内核 + 八份领域配置」——这样既有领域隔离，又不会带来多进程
> 编排和上下文丢失的代价。ReAct 是 Yao 等 2022 年论文（arXiv 2210.03629）的范式，LangGraph
> 只是 2024 年的一个实现框架；项目依赖与代码层面零引用 LangChain / LangGraph。

**Q2. 路由 Agent 怎么分派？一句话跨两个领域怎么处理？**

> 分派逻辑在 `react.py` 的意图阶段：规则先命中，没命中才请 LLM 判，纠偏还要过一遍角色画像。
> 判定出意图后映射到目标子 Agent（映射表与工具画像同源，不另立清单）。
> 复合意图的例子——「我家金毛拉稀，吃什么粮」：
> ① 路由识别为「健康症状咨询 + 饲养营养」；
> ② 因为两者有依赖，串行执行：健康问诊先判风险等级、给出忌口清单；
> ③ 结论作为上下文传给饲养营养，由它出饮食方案（有腹泻时不会给常规换粮建议）；
> ④ 合规风控校验有没有暗示治疗、有没有推荐禁用食物；
> ⑤ 路由合并成一条回复：先风险判断，再饮食方案，附来源引用。
> 无依赖的场景（比如「推荐个猫砂，店里有货吗」）才并行跑导购和库存查询。

**Q3. ReAct 循环具体怎么跑？**

> 主链路：用户输入 → 路由 Agent 意图识别（在主链路、延迟优先，用快模型）→ 确定目标子 Agent 与工具子集 → `react.py` 驱动「思考 → 调用工具 → 观察结果」的循环 → 产出最终回复或业务事件。工具调用前用 `inspect` 按签名过滤入参（防止 LLM 给无关槽位导致 TypeError），工具异常 rollback 后必须 `_recover_session()` 否则会 MissingGreenlet。

**Q4. 工具数量为什么要收敛到 11 / 13 个？**

> 实测发现工具池一旦过大，LLM 的工具选择准确率显著下降、提示词也过长。V8.3 给宠主加了 `search_knowledge` 后到 13 个，意图评测仍能 45/45，于是明确「宠主 ≤14、店员/店长 ≤11」的上限红线。收敛除了按端，也按 Agent——每个子 Agent 只挂自己领域的工具，健康问诊看不到商品库存工具。权限是「角色白名单 + 端内画像」双重判定：角色允许 ≠ 可调用，还必须在当前端的画像里。

**Q5. ★ 工具是怎么注册的？`@tool` 装饰器到底做了什么？**

> 不用 MCP、也不用 LangChain 的 `Tool` 类，是自研的装饰器 + 全局字典（`app/agent/tools/registry.py`）：
> ① 注册时 `inspect.signature(fn)` 取参数名，存进 `TOOLS[name]` 的 `params` 元组（`ctx` 排除）；
> ② 写入 `roles` 白名单，决定哪些角色能调；
> ③ 登记副作用：带写语义的工具自动加入 `WRITE_TOOLS`，`WRITE_INTENTS = set(WRITE_TOOLS)` 从它派生（禁止手写第二份清单）；
> ④ `tool_manifest(role)` 按画像生成给 LLM 的 function schema。
> 关键收益：**入参按签名过滤**——LLM 多给一个无关槽位也不会 `TypeError`，这是实测踩过的坑。

**Q6. ★ 工具执行抛异常了怎么办？为什么回滚了还会报错？**

> 两类处理：
> ① 可降级的检索类工具（知识检索、标签召回）在**工具内部** `try/except` 兜底，返回「未命中」而不是冒泡到 stream——否则一个检索失败会把整轮对话打断；
> ② 写类工具异常回滚事务后，SQLAlchemy 的 identity map 里还留着**已过期**的 ORM 对象，后续访问属性会抛 `MissingGreenlet`。所以 `react.py` 在 rollback 后强制调 `_recover_session(session)`，重新取一次会话对象再继续。
> 这是「回滚了事务不等于对象可用」的典型坑。

**Q7. ★ 意图识别放在哪个环节？规则和 LLM 谁说了算？**

> 规则优先、LLM 只做有限纠偏。流程是：
> ① 规则先命中（高风险写操作、确定性导航），命中即可定意图；
> ② 规则没命中才请 LLM 判意图，且**LLM 纠偏必须校验角色画像**——只能纠偏成 `smalltalk` 或当前画像内的工具，越出画像直接退回规则结论；
> ③ 兜底：当 LLM 判成 `smalltalk` 但文本命中「领域词 + 疑问词」且无动作词时，用 `_looks_like_knowledge_question()` 拉回知识问答，避免领域问题被当闲聊答掉。
> 设计取舍：意图识别在主链路、延迟敏感，用快模型；强但慢的模型放备选链。

**Q8. ★ 为什么「帮我看看宠物状态」不做成一个工具？**

> 因为它是**导航**，不是业务操作。项目约定「打开某个功能」优先理解为跳转：规则命中后直接下发 `navigate` 事件让前端切页，不走 LLM 工具调用。
> 理由很实在：功能页有完整的凭证签发、操作留痕、结束观看闭环；在聊天里复刻一份播放弹窗，必然和功能页行为不一致（这条被用户当场否掉过一次，属于血泪教训）。

**Q9. ★ 用户说不出精确房号 / 单号怎么办？**

> 做口语别名解析，而不是回「找不到」。`resolve_room()`（`app/services/boarding_service.py`）按三级兜底匹配：
> 房号精确匹配 → 房型别名（「大房」「豪华间」）→ 能装下该宠物的最便宜可订房。
> 仍然解析不出时，把「可选房型 + 起价」回给用户让他选，而不是甩一句「未找到房舍」。房号、单号这类东西用户记不住是正常的，接口要适配人。

### B. 安全与正确性（重点）

**Q10. 为什么写操作绝不交给 LLM 直接执行？怎么保证？**

> LLM 不可控：会幻觉、会越权、会绕过业务规则。我们做法是 Agent 只产出「意图 + 结构化参数」，真正的写库由业务服务层执行，服务层内置：① 权限校验（角色 + 归属）；② 状态机推进（只有合法的状态迁移才放行）；③ 数据库事务；④ `operation_log` 审计（手机号 AES+HMAC 脱敏）。代码铁律：写操作绝不经由 LLM 直跑。

**Q11. 写意图会不会被 LLM 误判成闲聊，导致操作静默丢失？**

> 这是特意封死的一条路。规则命中写操作时，LLM 只能把它纠偏成**另一个工具**，**不允许降级成 `smalltalk`**（`react.py` 里显式判断 `rule["intent"] in WRITE_INTENTS and llm_intent == "smalltalk"` 时保留规则结论）。
> 原因：闲聊分支不会触发任何服务层动作，用户会以为「说了但没生效」，比报错更难排查。

**Q12. 表单页面和 Agent 对话怎么保证走同一套逻辑？**

> 两者调用**同一个 Service 方法**，并用同一个 `idempotent_key` 幂等键。表单提交和「帮我在对话里下单」落库路径完全一致，不会出现「页面能下、对话不能下」或反之的分裂。

**Q13. ★ 手机号这类敏感信息怎么存？日志里怎么防泄漏？**

> 存储双写：**AES(Fernet) 密文**用于回显 + **HMAC 索引列**用于等值查询（密文每次加密结果不同，不能直接查）。
> 日志侧：日志层统一脱敏，业务代码即使 `logger.info(user.phone)` 打出来也是掩码，不依赖开发者自觉。

**Q14. ★ 为什么宠物档案（pet）反而没有归属限制？**

> 权限模型要跟现场排班对齐。早期按 `staff_id` 做了严格归属隔离，结果现场「借账号顶班」很普遍，拦太紧就被绕过，反而更乱。现在明确：**客户档案（含疫苗、驱虫）店员/店长可读可改全部**，`pet.staff_id` 只作建档溯源，不做权限边界；而**预约、洗护记录仍按归属隔离**（这两类涉及业绩与责任认定）。
> 一句话：权限不是越严越好，是要跟真实工作流一致。

### C. 并发与数据一致性

**Q15. MySQL REPEATABLE READ 下 `COUNT(*)` 是快照读，并发写你怎么解决？**

> 这是个真实踩过的坑：REPEATABLE READ 下普通 `COUNT(*)` 是快照读，并发写入后读不到最新行。解决是「加锁读 + 当前读」：用 `SELECT ... FOR UPDATE` 锁行，且 SQLAlchemy 必须加 `.execution_options(populate_existing=True)`，否则 identity map 会返回旧值。

**Q16. 会话级并发锁为什么是进程内 asyncio 锁？多实例怎么办？**

> 单实例时进程内 `asyncio.Lock` 足够防止同一会话并发写。但多实例部署时必须换成 Redis 分布式锁或 MySQL `GET_LOCK`，否则锁不住跨进程并发。这是明确写进项目约定的边界。

**Q17. ★ 幂等键 `idempotent_key` 具体怎么防重复下单？**

> 前端请求拦截器统一注入幂等键（`request.ts`），后端服务层在同一事务内先按该键查是否已处理：已存在直接返回上次结果，不存在才执行写入并登记。这样网络重试、用户连点、SSE 重连都不会产生第二单。
> 一个例外要处理：**multipart 上传不能带这个键**——`FormData` 硬塞字段会污染表单，所以上传接口显式加 `X-Skip-Idempotent: 1` 让拦截器跳过注入。

### D. RAG 知识底座（V8.5）

**Q18. RAG 为什么不做一个独立的知识库搜索页？**

> 因为检索的价值是**支撑回答**，不是「搜一段文本给用户看」。独立搜索页能返回的只有片段列表，
> 用户还得自己判断哪条可信、怎么用——真正的结论没产生。
> 现在的做法：检索是 Agent 的一个工具（`search_knowledge`），由 Agent 在对话链路内判断
> 「这轮需要专业知识」才调用；命中片段喂给模型生成答案，同时以 `refs` 事件把片段推到前端折叠展示，
> 用户既拿到结论，又能点开看依据。
> 知识库管理页只保留文档治理（上传 / 切块 / 任务状态 / 删除 / 重建），没有搜索框。
> 少一个入口就少一处要维护的权限与一致性：搜索页的权限规则、分页、空态、引用格式，
> 全部要在对话之外再实现一遍，而它带来的价值只是「同一批片段的另一种看法」。

**Q19. 知识库分片是怎么分的？为什么要分片？**

> 六个逻辑分片：疾病、营养膳食、饲养管理、行为心理、用品商品、门店私有（套餐 / 价格 /
> 到店须知 / 客户病历），用知识条目的 `category` 隔离。
> 分片的动机是**缩小候选集**：全库混检时，「猫砂盆多大合适」和「猫呕吐怎么办」在同一空间里抢分，
> 向量相似度容易串味；限定到用品商品分片后，候选从全量降到几十条，精度和延迟都更好。
> 检索时按目标子 Agent 限定分片——健康问诊查疾病库，用品导购查商品库，宠物档案查门店私有库。
> 数据来源只取宠物医学科普、正规兽医手册、AAFP / WSAVA 指南、门店自有资料，不采信自媒体偏方。

**Q20. 切块策略有哪几种？为什么要保留页码 / 段落 / 字符区间？**

> 三种（`app/rag/parser.py`）：按**标题**（`## ` 小节预切，默认）、**段落**、**固定长度**（可配块大小 100~4000、重叠 < 块大小且 ≤1000）。元数据保留 `page_start/page_end`、`paragraph_start/paragraph_end`、`char_start/char_end`、`source_label`（如「kb-test.md · 第6-7段 · 禁浴情形」），是为了**回答可溯源**——用户问「疫苗后多久能洗澡」，能精确回指到原文第几段，而不是糊一段摘要。

**Q21. 怎么保证向量索引新鲜？重复文件怎么识别？**

> （`app/rag/index.py`）索引建时锁死维度，collection 元数据记 `entries` 条数，检索前比对 DB 当前条目数，不一致自动 `reindex`。重复文件用 **SHA-256 内容哈希**识别：内容相同直接返回「与知识库 xxx 重复」，不重复写盘。不同 embedding 向量不可混查，空召回退标签兜底。

**Q22. ★ 为什么切块要先按 `## ` 预切，再交给 SentenceSplitter？**

> 顺序不能反。SentenceSplitter 只认字数，如果直接 500/50 切，会把「洗澡水温」的正文和小节标题切断，出现**文档检索对了、但片段所在段落错了**的情况——引用回指时指向无关小节。
> 现在的做法是两级：先按 `## ` 的小节边界预切（保证语义单元的边界不被破坏），每个小节内部再用 `SentenceSplitter(500, 50)` 处理超长部分。宁可块大小不均匀，也不能跨小节混块。

**Q23. ★ 上传的文档本来就是切好的块，入库时还会被再切一次吗？**

> 不会，这是特意避开的坑。`_build_index` 里对内置条目走 `split_sections + SentenceSplitter`，但对**上传块**（`pre_chunked=True`）直接构造 `TextNode(text=..., metadata=...)` 塞进索引，跳过 splitter。
> 否则用户按「段落」策略精心切的块，会被默认 500/50 再切一遍，切块策略形同虚设，元数据（页码、段落区间）也会和实际文本对不上。

**Q24. ★ 检索结果的阈值怎么定？全都不过阈值怎么办？**

> 双阈值（`app/rag/index.py`）：rerank 分 ≥ `MIN_RERANK_SCORE`（0.45）、向量分 ≥ `MIN_VECTOR_SCORE`（0.30），两路结果去重后合并（`("chunk", id)` / `("entry", id)` 作键，避免同一段被两条链路各命中一次）。
> 关键兜底：**如果全部不达标，保底保留最高分那一条**并标注「匹配度较低」，而不是返回空。返回空会让上层误判成「知识库没有这条」，实际只是措辞不同。

**Q25. ★ RAG 的回答和引用怎么给前端？刷新页面后引用还在吗？**

> 回答是「检索 + 生成」两段：命中的片段喂给模型生成自然语言答案，同时把片段以 **`refs` 事件**流式下发（`react.py` 里 `yield {"type": "refs", ...}`），前端渲染成可折叠的「参考来源」面板。
> 刷新页面后靠历史消息里的 **`tool_result`** 还原引用，不额外新增数据库列——引用本来就是某次工具调用的产物，重复存储会导致两处数据不一致。

**Q26. ★ embedding 走批处理，batch 为什么是 10？**

> 百炼 embedding 接口**单次最多 10 条**，超了整个请求会被拒。所以 `embed_batch_size=10` 是硬约束不是调优参数，写死在 `app/rag/index.py`。
> 另外向量维度在建 collection 时就锁死，换 embedding 模型只能重建索引（不同模型向量不可混查），靠侧车 `space.json` 记录当前 space 做隔离。

### E. 异步任务与可靠性

**Q27. 上传文件后切块入库是异步的，进程重启了未完成的任务怎么办？**

> 入库走 `asyncio.create_task` + `Semaphore(2)` 限并发 + 索引串行锁，任务状态写 `knowledge_ingest_task` 表（pending→processing→completed/failed + 进度 + 失败原因）。**启动时 `resume_unfinished_tasks()` 把未完成任务重新排队**，所以进程崩了 / 重启了不会丢任务。前端 3 秒轮询查进度，不用 SSE（避免长连接把冒烟挂死）。

**Q28. ★ 为什么要限并发 2？索引为什么又要串行？**

> 两种资源两种约束：
> ① **限并发 2** 是因为解析 PDF、算 embedding 都是 CPU + 外部 API 消耗型操作，同时跑多个会互相拖慢，还可能撞百炼限流；信号量把并发压住，保证单个任务能跑完。
> ② **索引串行** 是因为 Chroma 追加/删除不是并发安全的，两个任务同时 reindex 会出现向量库条目数和 DB 对不上。用一把 `asyncio.Lock` 把「重建索引」整段包起来，任务只能排队等。
> 一个细节：入库流程里**先提交 `document.status=completed` 再拿索引锁**，因为 reindex 会从独立查询里读块，未提交就看不见新块（E-78）。

**Q29. ★ 任务失败后用户能看到什么？会不会卡在「处理中」？**

> 不会卡住。失败时 `_set_failure()` 一次性写三样：任务 `status=failed` + `error_message`（具体原因，如「扫描版 PDF 无可提取文本，需 OCR」）+ 文档 `status=failed`，前端按这三种状态分别展示。
> 每个上传文件独立 try/except，一批 5 个文件里坏 2 个，其余 3 个照常入库，失败项逐个回显原因——不做「一个失败全批回滚」，那样用户得反复重传。

### F. 工程与测试

**Q30. 你怎么做测试保障？覆盖率门槛多少？**

> 三层验证：① 后端 `pytest`（服务层 `--cov-fail-under=80`，实测 **82.05%**）；② `scripts/smoke_test.py` 冒烟（API 级，261 项）；③ 浏览器端到端 `verify-spa.mjs`（CDP 连 headless Edge，123 项）。改完必跑三层。关键原则：**断言不依赖模型措辞**（否则历史数据会打成假失败），用「有实质回复 + 说到业务对象」判断。

**Q31. ★ 为什么覆盖率只卡服务层，不卡全仓？**

> 因为卡全仓会逼着人给路由、schema、常量写无意义断言凑数字。项目里真正出 bug 的地方是服务层（事务、状态机、并发），所以 `pytest.ini` 固定 `--cov=app.services --cov-fail-under=80`。
> 副作用也要接受：把 `rag_index.py`（386 行）从 `services` 挪到 `app/rag` 包后，分母变小，覆盖率从 81.4% 升到 82.05%——数字变化不代表代码变好，要能解释清为什么。

**Q32. ★ 测试用例怎么保证互不干扰、不留垃圾数据？**

> 两条硬规矩：
> ① **用例只依赖自己造的数据**，不读库里现成的宠物/订单——否则别人加了数据就会把你的断言打破；
> ② **用例产物必须有回收路径**：宠物、摄像头、知识文档都曾因为没回收累积到 47 只 / 49 台，后来统一在 teardown 清理，并加了 `cleanup_pets.py` / `cleanup_business.py` 兜底。
> 另外测错误处理时 `TestClient` 必须关 `raise_server_exceptions=False`，否则异常直接抛到测试里，测不到你的错误响应格式。

**Q33. 配置管理有什么原则？**

> 所有可变参数（块大小、文件上限、模型名、版本号）集中在 `app/constants/enums.py` 和 `app/config.py`，业务只从 `app.constants` 导入，**禁止硬编码**。`APP_VERSION` 在 `.env` 有配置项，改类默认值无效，必须同时改 `.env` 与 `.env.example`。凡「新增 A 必须同步改 B」一律改成从 A 派生 B。目录类配置用锚点绝对路径，避免按 cwd 解析导致文件散落（曾踩过两个向量库分裂的坑）。

**Q34. ★ 前端上传进度和格式校验是怎么做的？**

> 上传用 Element Plus 的 `el-upload`（拖拽 + 多选），`http.post` 的 `onUploadProgress` 里按 `loaded/total` 算百分比，只在上传阶段显示进度条（解析切块阶段是异步任务，切到「任务」页签看状态）。
> 校验双层：前端先按扩展名和大小快速拦（体验），后端再权威校验（安全）——前端永远不可信。单个文件失败不影响其他文件，返回体里 `items` + `failed` 分开，UI 逐条标红并给原因。
