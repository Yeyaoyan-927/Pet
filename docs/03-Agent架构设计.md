# Agent 架构设计（多 Agent 协作 · 架构基线）

> **状态**：本文描述的多 Agent 架构**已落地**（对话与工具细节见 [`04-Agent对话与工具说明.md`](04-Agent对话与工具说明.md)）。
> 交付状态：**DoD 全部完成**（路由分发 / 领域子 Agent / RAG 知识底座 / 意图评测集 / 会话级并发锁均已落地）。
>
> **架构约定（硬约束，不得偏离）**
>
> 1. **多 Agent 分工协作**：一个路由调度 Agent 负责意图判定与任务分派，领域子 Agent 各司其职，
>    统一入口对外只呈现一个对话窗口。
> 2. **RAG 是所有 Agent 的统一知识底座**：任何涉及专业知识、门店政策、商品参数的回答，先检索知识库再生成，
>    检索在**对话链路内**由 Agent 自主触发，不设独立的知识检索页面。
> 3. **业务闭环用状态机 / Graph Workflow**：预约、寄养、订单等流程由显式状态机驱动，子 Agent 不得自行判定状态合法性。
> 4. **写操作绝不交给 LLM**：LLM 只能「决定调用哪个工具」，工具内部一律走业务服务层
>    （权限 → 状态机 → 事务 → 审计），既不拼 SQL，也不绕过校验。
> 5. **Agent 之间不自由协商**：跨 Agent 协同由路由 Agent 按显式编排规则串行/并行调度，禁止子 Agent 之间互相委派。

## 一、为什么选多 Agent 协作

| 方案 | 问题 | 本项目的取舍 |
| --- | --- | --- |
| 单一大模型直连业务 | 幻觉导致错误写库；专业领域回答无依据；无法保证业务规则 | ❌ 不采用 |
| 自由协商式多 Agent 框架（CrewAI / AutoGen） | 角色间自由对话导致流程不可预测、责任边界模糊、调试与审计困难 | ❌ 不采用 |
| **路由调度 + 领域子 Agent + 显式编排** | 专业域隔离、提示词与工具集收敛、每步可审计可重放 | ✅ 采用 |

核心原因有两个：

1. **专业域差异大**。健康问诊要严守「不诊断、不开处方」的红线，用品导购要贴着库存和价格说话，
   档案 Agent 要读写长期记忆——把它们的提示词和工具塞进同一个决策点，个别领域的规则会被稀释。
   拆成子 Agent 后，每个域只带自己的领域提示词和工具白名单，规则不被污染。
2. **门店业务是规则密集、状态强约束的场景**（时段容量、状态机、风险前置）。
   多 Agent 只分担「专业判断」，不接管「流程正确性」——流程仍由状态机保证。

**与业界框架的区别**：本项目不引入任何多 Agent 框架，编排规则、路由判定、上下文传递都是自研的
（`app/agent/react.py` + `app/agent/tools/profiles.py`）。子 Agent 不是独立进程或独立模型实例，
而是「共享同一个 ReAct 执行内核 + 各自的领域提示词与工具子集」的逻辑 Agent。

## 二、分层架构

```
┌──────────────────────────────────────────────────────────────────┐
│ 交互层   宠主端对话  |  店员端对话  |  店长端对话  |  WEB 表单      │
└───────────────────────────┬──────────────────────────────────────┘
                            │ HTTP / SSE
┌───────────────────────────▼──────────────────────────────────────┐
│ 路由调度 Agent（Router）                                           │
│   意图识别 → 领域判定 → 任务分派 → 结果合并 → 统一出口              │
└───────┬──────────────────────────────────────────────┬───────────┘
        │ 分派（显式编排，不自由协商）                    │ 并行校验
┌───────▼──────────────────────────────────┐  ┌────────▼──────────┐
│ 领域子 Agent                              │  │ 合规风控 Agent     │
│  ├─ 健康问诊    ├─ 饲养营养                │  │  急症识别          │
│  ├─ 行为训练    ├─ 用品导购                │  │  处方/诊断拦截     │
│  ├─ 宠物档案    ├─ 门店业务                │  │  偏方与禁忌食物     │
│  └─ 经营分析    └─ (店长/店员可见)          │  │                    │
└───────┬──────────────────────────────────┘  └────────┬──────────┘
        │ 工具调用（唯一通路）                            │
┌───────▼──────────────────────────────────────────────▼───────────┐
│ 业务服务层（唯一写入口）                                            │
│ appointment / boarding / goods / pet / risk / setting / knowledge │
│ 权限 · 状态机 · 事务 · 审计                                        │
└───────┬──────────────────────────────────────────────────────────┘
        │ 知识检索（对话内触发）
┌───────▼──────────────────────────────────────────────────────────┐
│ RAG 知识底座（6 个逻辑分片）                                        │
│ 疾病 · 营养膳食 · 饲养管理 · 行为心理 · 用品商品 · 本地私有          │
└──────────────────────────────────────────────────────────────────┘
```

**关键约束**：Agent 层与业务服务层之间只有「工具调用」这一条通路，
Agent **无法**直接访问数据库 Session，物理上杜绝 LLM 直连写库。

## 三、Agent 清单与职责

### 3.1 路由调度 Agent（入口）

| 项 | 说明 |
| --- | --- |
| 职责 | 意图识别、领域判定、任务分派、多 Agent 结果合并、统一出口 |
| 输入 | 用户原话 + 会话记忆 + 当前角色 + 宠物档案摘要 |
| 输出 | 意图标签 + 目标子 Agent + 槽位；或直接回复（闲聊 / 寒暄） |
| 实现 | `react.py` 的意图阶段：规则优先，LLM 纠偏；纠偏必须校验角色画像 |

意图标签（与工具画像同源，禁止另立一套清单）：

| 标签 | 目标 Agent | 说明 |
| --- | --- | --- |
| 健康症状咨询 | 健康问诊 | 呕吐、腹泻、皮肤、精神萎靡等 |
| 喂食 / 营养 | 饲养营养 | 喂食量、换粮、营养品、禁忌食物 |
| 行为训练 | 行为训练 | 拆家、吠叫、护食、乱尿、应激 |
| 用品推荐 | 用品导购 | 猫砂、粮、玩具、用品适配 |
| 档案查询 / 建档 | 宠物档案 | 疫苗、驱虫、体重、既往病史 |
| 预约 / 洗护 / 寄养 / 实景 | 门店业务 | 查时段、下单、改期、取消、看实景 |
| 闲聊 | —（直接回复） | 不消耗工具 |
| 高危急症 | 风控（强制） | 抽搐、大出血、呼吸困难、中毒 → 立即中断普通问答 |

> 规则先命中、LLM 后纠偏。规则命中写操作时，LLM 只能把它纠偏成**另一个工具**，
> **不允许降级成 `smalltalk`**——否则用户会以为「说了但没生效」，比报错更难排查。

### 3.2 领域子 Agent

| Agent | 能做 | 严格禁止 | 依赖 |
| --- | --- | --- | --- |
| **健康问诊** | 预问诊信息收集（年龄/疫苗/驱虫/呕吐次数/便血/精神/体温）、症状鉴别、风险分级（低危 / 观察 / 尽快就医 / 立刻急诊）、居家护理与禁忌提醒 | 开处方、确诊疾病、替代执业兽医 | 疾病库 + 用药禁忌 + 中毒急救清单 |
| **饲养营养** | 喂食量与频次、粮选择、自制食谱、7 天换粮过渡、营养品是否补充 | 推荐处方粮替代治疗、承诺疗效 | 营养膳食库 + 品种易发病饮食 |
| **行为训练** | 分步正向训练流程、环境调整方案、行为原因分析 | 体罚 / 电击项圈等伤害性方案 | 行为心理学库 + 正向训练手册 |
| **用品导购** | 选型标准、避坑点、适配品类、门店在售商品匹配（价格/库存） | 无依据的品牌硬推、夸大功效 | 用品商品库 + 门店商品库 |
| **宠物档案** | 读档案给其他 Agent 作上下文、经用户确认后写入本次关键信息、按名字/手机号检索客户档案 | 未经确认自动改写宠物档案；**到期提醒不在此 Agent**（由 `app/tasks` 定时任务承担） | `pet` / `vaccine_record` / `operation_log` |
| **门店业务** | 查时段、创建/改期/取消预约、寄养下单、用品下单、洗护记录、实景凭证 | 绕过状态机改状态、跳过风险前置 | 业务服务层全部服务 |
| **经营分析** | 经营指标、时段饱和度、流失预警、员工业绩、待办看板、审计与门店配置（仅店员/店长） | 给宠主看门店经营数据、替店长做决策承诺 | `stats_service` / `schedule_service` / `audit_service` |

### 3.3 合规风控 Agent（横切）

每一轮回答**都过一遍**，与业务 Agent 并行校验：

- 是否给出处方药、剂量或诊断结论？
- 是否淡化了急症风险（把「需要立刻就医」说成「观察一下」）？
- 是否出现偏方、有毒食物（巧克力 / 葡萄 / 洋葱 / 老鼠药）推荐？
- 识别到高危情况 → **强制拦截**，输出「立刻送宠物医院」，同时把急症标记写进会话。

风控是**否决权**而不是建议权：它判定不合规时，无论领域 Agent 生成了什么，最终出口都会被改写。

**它为什么不是「第 10 次模型调用」**：合规是确定性要求——「不能下诊断」「不能给剂量」
这几条必须每次都判得一样。再叫一次模型来判，只会引入随机性、多一次延迟、多一个失败点。
所以实现是**出口上的一道规则闸门**（`app/agent/compliance.py`）：

| 规则 | 命中后动作 |
| --- | --- |
| 急症信号（抽搐 / 大出血 / 呼吸困难 / 中毒 / 尿闭 / 便血…） | 回答**前置**「立刻送宠物医院，不要在家观察」 |
| 诊断 / 处方表述（确诊 / 就是 XX 病 / 阿莫西林 / 剂量 / mg/kg…） | 回答**后置**免责声明「不构成医疗诊断」 |
| 有毒食物被当成推荐（「可以吃巧克力」） | **改写为警告**，优先级最高 |
| 健康语境（就医 / 症状 / 吃药 / 诊断…） | 统一**后置**免责声明——只看「有没有命中诊断词」会漏掉「门店不做诊断、请带去医院」这类正确表述 |

只作用于知识问答 / 健康类回答（`search_knowledge`、`query_risk_report`、`confirm_risk`），
闲聊、槽位追问、确认卡不受影响——避免在「请确认是否提交预约」后面挂一句医疗免责。
命中记录写入日志 `compliance_triggered`（带 flags），便于复盘。

### 3.4 跨 Agent 协同

用户说「我家金毛拉稀，吃什么粮？」——一句话跨两个域：

```
[路由] 意图 = 健康症状咨询 + 饲养营养（复合意图）
   ↓ 串行（有依赖）
[健康问诊] 评估风险等级 → 输出「观察 / 就医」结论与忌口清单
   ↓ 结论作为上下文
[饲养营养] 基于风险结论给饮食方案（若无腹泻则常规换粮建议）
   ↓
[合规风控] 校验：是否暗示了治疗？是否推荐了禁用食物？
   ↓
[路由合并] 单一回复：先给风险判断，再给饮食方案，附来源引用
```

编排规则写死在路由层：**健康判断永远先于营养建议**（有依赖的串行），
「用品推荐 + 门店有货」这类无依赖的场景才并行。子 Agent 之间不直接对话，上下文由路由层传递。

## 四、RAG 知识底座

### 4.1 分片设计

| 知识分片 | 内容示例 | 主要服务 Agent |
| --- | --- | --- |
| 疾病库 | 常见病症、症状鉴别、急症识别、用药禁忌、中毒急救 | 健康问诊 / 风控 |
| 营养膳食库 | 各年龄段粮配方、生骨肉与熟自制配比、换粮方案、营养品、禁忌食物 | 饲养营养 |
| 饲养管理库 | 驱虫时间表、疫苗流程、洗澡频率、绝育护理、孕产与老年养护 | 宠物档案 / 健康问诊 |
| 行为心理学库 | 应激、分离焦虑、护食、扑人、乱尿成因、正向训练方案 | 行为训练 |
| 用品商品库 | 猫砂、笼具、牵引、猫抓板、自动喂食器适配标准与避坑点 | 用品导购 |
| 本地私有库 | 本店套餐、医生排班、院内药品、价格、到店须知、客户既往病历 | 门店业务 / 宠物档案 |

分片通过知识条目的 `category` 隔离，检索时按目标 Agent 限定分片范围——缩小候选集，比全库混检更准。

> 数据来源只取宠物医学科普、正规兽医手册、AAFP / WSAVA 指南、门店自有资料，**不采信自媒体偏方**。
> 当前已填充以洗护安全与饲养管理为主，其余分片按门店业务增量上传。

### 4.2 检索在对话内完成

**没有独立的知识检索页面。** 检索是 Agent 的一个工具（`search_knowledge`），由 Agent 在对话中自主决定是否调用：

```
用户提问 → 路由判定需要专业知识 → 健康问诊 Agent
   ↓
search_knowledge(query, category=疾病库)   ← 对话链路内触发
   ↓
多路召回（向量 + 关键词标签）→ rerank 精排 → 阈值过滤（0.45 / 0.30）
   ↓
片段喂给模型生成回答 + 片段以 refs 事件下发前端折叠展示
```

知识库管理页（店长）只负责**文档治理**：上传、切块、查看任务状态、删除、重建索引。
「检索」这个动作只存在于对话里——因为检索的价值是「支撑回答」，脱离回答单独搜一段文本，用户拿不到结论。

**拒答规则**：知识库没有、或涉及需要面诊判断的疾病，明确引导线下就医，不猜测、不开药。

### 4.3 入库流水线

```
上传 → 校验（20MB / 单次 5 个 / SHA-256 去重）
     → 解析（PDF / DOCX / TXT / MD，保留页码与段落）
     → 切块（标题 / 段落 / 固定长度，块大小 100~4000、重叠 < 块大小且 ≤1000）
     → 异步写块（并发 2 + 索引串行锁）
     → 重建向量索引
```

切块一律保留 `page_start/page_end`、`paragraph_start/paragraph_end`、`char_start/char_end` 与
`source_label`，回答能精确回指「哪篇文档 · 第几段 · 哪个小节」。

### 4.4 记忆分层

| 层 | 存储 | 生命周期 | 说明 |
| --- | --- | --- | --- |
| 长期记忆 | `pet` / `vaccine_record` / `operation_log` | 永久（按合规留存） | 每只宠物独立档案：品种、年龄、绝育、过敏、既往病史、上次问诊 |
| 会话记忆 | `chat_session` / `chat_message` | 按 `session_retention_days` 清理 | 滑动窗口 + 摘要压缩 |
| 知识记忆 | Chroma 向量库 | 随知识条目增删 | 静态专业知识，所有 Agent 共享 |

三者严格分离：RAG 是**静态知识**，档案是**用户私有动态记忆**，会话是**当前对话上下文**。
问答时三者同时注入，但写回路径完全不同——只有档案 Agent 能经用户确认后写档案，RAG 只读。

## 五、三端差异：同一套 Agent，不同可见性

三个端共用一套 Agent 定义与同一个执行内核，差异体现在**可激活哪些 Agent** 与 **Agent 内的工具白名单**。
下表的勾选由 `app/agent/agents.py` 的 `roles` 声明，与 `ROLE_TOOL_PROFILE` 的工具画像一一对齐。

| Agent | 宠主端 | 店员端 | 店长端 |
| --- | --- | --- | --- |
| 路由调度 | ✅ | ✅ | ✅ |
| 健康问诊 | ✅ 完整预问诊 | ✅ 预问诊辅助（看风险等级、复核） | ❌ |
| 饲养营养 | ✅ | ✅ | ❌ |
| 行为训练 | ✅ | ✅ | ❌ |
| 用品导购 | ✅ 面向自己的宠物 | ❌ | ❌ |
| 宠物档案 | ✅ 仅自己名下宠物 | ✅ **全部客户档案可读写** | ❌ |
| 门店业务 | ✅ 预约/寄养/用品/实景 | ✅ 开单、改期、核销、照护记录 | ✅ 含 SLA 处置 |
| 经营分析 | ❌ | ✅ 看板与统计 | ✅ 含审计与门店配置 |
| 合规风控 | ✅ | ✅ | ✅ |

**数量**：1 路由 + 7 领域 + 1 风控 = **9 个 Agent**；可激活数按端裁剪：
宠主 8 个、店员 8 个、店长 4 个（路由 + 门店业务 + 经营分析 + 风控）。

工具数量按端收敛：**宠主 13 个 / 店员 11 个 / 店长 11 个**（工具池 30 个）。
收敛不是权限的替代品，而是叠加：**角色白名单通过 ≠ 可调用，还必须在当前端的画像内**。

> 档案权限的一个刻意例外：客户档案（含疫苗、驱虫）对店员/店长**不做归属隔离**。
> 现场「借账号顶班」很普遍，拦太紧会被绕过反而更乱；`pet.staff_id` 只作建档溯源。
> 预约与洗护记录**仍按归属隔离**——这两类涉及业绩与责任认定。

## 六、执行内核：ReAct 循环

所有 Agent 共享同一个执行器，循环四步，每步产出结构化事件（可流式输出到前端）：

```
1. Thought     读取用户输入 + 会话记忆 + 已收集槽位 + 档案摘要，判断意图与下一步
2. Action      选择 1 个工具（或直接回复），参数由 LLM 以 JSON 输出并做 Schema 校验
3. Observation 执行工具，拿回结构化结果（仅查询结果或写操作回执）
4. Loop        未完成 → 回到 1；完成或达到最大轮次(默认 6) → 生成最终回复
```

**安全边界**：

- 单轮只允许 1 个工具调用，禁止并行写操作；
- 工具参数按**函数签名过滤**（`inspect.signature` 收集参数名，执行前剔除非签名槽位），
  防止 LLM 多给字段导致 `TypeError`；
- 工具执行异常 rollback 后必须 `_recover_session()` 重新取会话对象，
  否则 identity map 里的过期对象会抛 `MissingGreenlet`；
- 达到最大轮次或连续 2 次工具失败 → 结束循环并提示转人工 / 表单入口；
- 全部轮次写入会话表与审计日志（`module=agent`）。

**确定性动作不下放给模型**：跳转页面、开关摄像头这类动作用规则直接触发，下发 `navigate` 事件。
功能页有完整的凭证签发、操作留痕、结束观看闭环，在聊天里复刻一份必然不一致。

## 七、Graph Workflow：业务闭环显式状态图

模糊的自然语言由 LLM 理解，但**流程骨架是显式状态图**，不是让 LLM 自由编排：

```
[START] 用户输入
   ↓
[intent] 意图识别（LLM，输出枚举：query_slots / create_appt / query_appt / cancel_appt /
   │              reschedule / query_risk / query_report / smalltalk）
   ├─ smalltalk ──────────────────────────────→ [reply] 直接回复 → [END]
   ↓
[collect_slots] 槽位收集（缺失则追问；最多追问 3 轮）
   ↓
[validate] 前置校验（必填槽位齐全？宠物归属？日期时段合法？权限？）
   ├─ 不通过 ─→ [reply_hint] 给出具体原因与可选值 → [END]
   ↓
[confirm] 危险写操作二次确认（取消 / 改期 / 代客预约）
   ├─ 用户取消 ─→ [END]
   ↓
[execute] 调用业务服务层工具（事务 + 状态机 + 审计）
   ├─ 业务异常 ─→ [reply_hint] 回显失败原因 → [END]
   ↓
[reply] 结构化回执（单号 / 到店时间 / 状态 / 风险提示）
   ↓
[END]
```

**为什么用状态图而不是纯 ReAct**：写操作路径必须**可枚举、可测试、可审计**。
ReAct 负责「理解与选工具」，Graph 负责「流程与闸门」，两者职责分离。

**与后端状态机的关系**：Graph 的 `[execute]` 必须调用业务服务层的状态迁移方法，
后者才是状态的唯一权威（`APPOINTMENT_TRANSITIONS` / 寄养状态机）；Graph 只是编排，不得自行判定状态合法性。

## 八、工具集：按 Agent 归组，全部复用业务服务层

工具池 30 个（`app/agent/tools/registry.py`），按 Agent 归属分组：

| Agent 归组 | 典型工具 | 类型 |
| --- | --- | --- |
| 门店业务 | `query_slots` / `create_appointment` / `cancel_appointment` / `reschedule_appointment` / 寄养与用品下单 | 读 + 受控写 |
| 宠物档案 | `query_pet_profile` / 档案与洗护历史查询 / 建档 | 读 + 受控写 |
| 健康问诊 | `query_risk_report` / 症状预问诊录入 | 读 + 受控写 |
| 经营分析（店长） | `query_report_summary` / 经营指标查询 | 读 |
| 知识检索 | `search_knowledge` / `query_report_summary` 等 | 读 |

**统一要求**：

- 通过 `@tool` 装饰器登记（名称 / 说明 / 是否写操作 / 角色白名单），
  写语义的工具自动进入 `WRITE_TOOLS`，`WRITE_INTENTS = set(WRITE_TOOLS)` 从它派生——禁止手写第二份清单；
- 每个工具声明 JSON Schema（入参出参），LLM 只能产出符合 Schema 的参数；
- 受控写工具必须携带 `idempotent_key`，与表单入口共用同一幂等键规范 → 双入口结果一致；
- 工具执行前后写审计日志，`module=agent`，`action=tool:<name>`。

## 九、模型层

> 接入方式：DashScope **OpenAI 兼容模式**（`/compatible-mode/v1`），httpx 直连，零额外 SDK 依赖；
> 型号全在 `.env` 配置，代码零硬编码。

- **主备链**：`qwen3.7-max-2026-06-08`（主）→ `glm-5.1`（跨厂商兜底），通过 `LLM_MODEL` / `LLM_FALLBACK_MODELS` 配置；
  `qwen-max` 免费额度耗尽（403）已停用。两个都不可用时降级到规则引擎，业务不中断。
- **职责分层**：意图识别在主链路、延迟敏感，用快模型；强但慢的模型放备选。
  路由调度对延迟最敏感，领域子 Agent 可以在生成阶段用更强的模型。
- **自动回退**：主模型额度用尽 / 限流 / 鉴权失败 / 超时 → 依次切换备选；全部失败 → 回退规则引擎。
- **JSON 强约束**：ReAct 与风险摘要均要求 `response_format=json_object`，
  并用 `extract_json()` 容错「纯 JSON / 围栏 / 夹带自然语言」三种形态，解析失败即降级。
- **可观测**：`GET /api/v1/agent/llm/status[?probe=true]`、`GET /api/v1/agent/llm/probe-models`、
  `scripts/check_llm.py`；日志事件 `llm_risk_enhanced / llm_risk_enhance_failed / llm_call_failed`。

**模型职责边界（不可越界）**：

| 环节 | LLM 能做 | LLM 不能做 |
| --- | --- | --- |
| 风险摘要增强 | 依据档案 + 规则结果生成摘要与建议 | 新增无档案依据的风险项、上调风险等级、写库 |
| 路由意图识别 | 输出意图枚举、目标 Agent 与槽位 | 编造用户未提供的槽位 |
| 工具选择 | 决定「调用哪个工具、传什么参数」 | 直接执行写操作、拼接 SQL |
| 业务写操作 | — | **绝对禁止**（必须经业务服务层） |

## 十、双入口一致性保障

| 一致性点 | 保障机制 |
| --- | --- |
| 业务规则 | 表单与 Agent 调用**同一个 Service 方法**，无第二套实现 |
| 幂等 | 统一 `idempotent_key` 字段 + 数据库唯一索引，重复提交返回同一订单 |
| 权限 | 复用 `deps/auth.py` 的角色守卫与归属校验 |
| 状态机 | 复用状态迁移表，非法流转一律 409 |
| 审计 | 两条入口都写 `operation_log`，可按 `biz_id` 汇总完整轨迹 |
| 风险判别 | 两条入口都在创建预约后触发同一 `assess_risk()` |

## 十一、会话与合规

- **会话表**：`session_id / user_id / turn / role / content / tool_calls / created_at`。
- **记忆策略**：滑动窗口（最近 N 轮）+ 摘要压缩（超长历史由 LLM 摘要）；
  敏感字段在入库前脱敏，不存手机号明文（AES 密文 + HMAC 索引双列）。
- **留存与清理**：按门店配置 `session_retention_days` 到期物理删除，由定时任务 `session_cleanup` 执行。
- **合规**：风险/健康类回答固定附带免责声明（「不构成医疗诊断」），与 `risk_service.DISCLAIMER` 一致。

---

## 十二、异常与回退策略

| 异常 | 处理 |
| --- | --- |
| LLM 超时 / 报错 | 规则引擎兜底：风险判别回退 `engine_type=rule`；对话入口提示转表单 |
| 路由判定失败 | 退化为「通用助手」模式，直接用当前端画像内的工具作答，不强行分派 |
| 子 Agent 返回为空 | 路由层补一句「这块建议咨询店员」，不返回空响应当作「没话说」 |
| 工具返回业务异常（如时段已满） | 不重试，直接把业务 message 回显给用户并给出可选时段 |
| 工具连续 2 次失败 | 终止 ReAct 循环，提示改用表单入口或联系店员 |
| RAG 检索不可用 | 跳过知识增强，仅用规则结果生成摘要，标记 `knowledge_refs=[]` |
| 会话超时 | 提示重新开始，不保留半途槽位 |
