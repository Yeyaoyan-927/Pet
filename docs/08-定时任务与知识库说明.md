# 定时任务、并发安全与 RAG 知识库（V6）

> 本文记录 V6「能力补全与工程加固」的三项核心交付：**定时任务闭环**、**时段并发防超卖**、**RAG 洗护安全知识库**，
> 以及配套的**意图识别评测集**。V6 没有新增 UI，交付物是能力与工程质量。

---

## 一、决策记录：为什么没有引入 arq + Redis

规划书原定用 **arq + Redis** 承载定时任务。实际落地时改为**进程内置调度器**，理由：

| 维度 | arq + Redis | 内置调度器（本版实现） |
|---|---|---|
| 新增依赖 | Redis 服务 + arq 库 | **零** |
| 部署复杂度 | 需额外进程与中间件，交付文档 `docs/09` 要写一整套 | 随应用启动，一条命令 |
| 本场景契合度 | 高频、耗时、需水平扩展的任务队列 | 5 个低频任务（15 分钟 ~ 1 天一次） |
| 能力缺口 | —— | **没有任何业务能力缺失**（SLA 巡检 / 提醒 / 清理全部落地） |

**关键设计：任务逻辑与调度器解耦。** 所有任务写在 `app/tasks/jobs.py`，只依赖 `AsyncSession`：
换 arq / Celery 时把 `JOBS` 注册成 worker 任务即可，**业务代码一行不用改**。
因此这不是「放弃 arq」，而是「先不引入不必要的运维负担，且随时可切」。

## 二、调度器设计（`app/tasks/scheduler.py`）

- **心跳 30 秒**：只判断「哪个任务到点了」，到点则顺序执行（顺序而非并发，避免同时写库互相锁等）。
- **启动延迟 30 秒**：避开应用启动事务与连接池预热。
- **调度器自身永不退出**：单轮异常被捕获并记日志，不影响主进程与其他任务。
- **失败隔离**：单个任务抛错 → 只标记该任务 failed，其他任务照常。
- **开关**：`TASK_SCHEDULER_ENABLED=false` 可整体关闭（测试 / 本地调试用）。

### 多实例安全（不靠 Redis 也能多开）

新增 `task_run` 表，一表两用：

1. **执行状态持久化** —— 记录 `last_started_at / last_finished_at / last_status / last_summary / run_count`。
   进程重启后据此判断「距上次执行是否已超过间隔」，**不会立刻重跑**。
2. **多实例互斥** —— 执行前对该任务行加 `SELECT ... FOR UPDATE NOWAIT`：
   拿不到锁说明别的实例正在跑，**立即跳过**（不等待、不重复执行）。

> 这是同一套「行锁」思路的第二次应用：时段容量用 `slot_lock`，任务互斥用 `task_run`。
> 相比于引入 Redis 分布式锁，它复用了既有基础设施，且锁随事务自动释放，不存在锁泄漏。

## 四、时段并发防超卖（`slot_lock` 行锁 + 当前读）

### 问题

预约创建是 check-then-act：先 `COUNT` 校验容量，再 `INSERT`。两个并发请求会同时通过校验，最终写入超额订单。

### 方案选型

| 方案 | 结论 |
|---|---|
| MySQL `GET_LOCK()` | 连接级命名锁，需显式释放，忘记释放会占满连接 ❌ |
| Redis 分布式锁 | 引入新中间件 ❌ |
| **锁行表 + `FOR UPDATE`** | 锁随事务提交/回滚自动释放，跨库通用，零新依赖 ✅ |

### 实现

```
_lock_slot(date, slot)         -- INSERT ... ON DUPLICATE KEY UPDATE 保证锁行存在
                              -- 再 SELECT ... FOR UPDATE 取行锁（先串行化）
_check_capacity(date, slot)    -- SELECT id ... FOR UPDATE（当前读）取真实占用量
INSERT appointment
commit                         -- 锁在此释放
```

### ⚠️ 这里有一个必须记住的坑：**加了锁照样超卖**

第一版只加了 `_lock_slot`，容量校验仍是 `SELECT COUNT(*)` —— 实测 **6 并发 6 单全部成功**。
根因：MySQL 默认隔离级别是 **REPEATABLE READ**，`SELECT COUNT(*)` 是**快照读**，
等锁的事务读到的仍是「自己事务开始时的旧快照」，看不到前一个事务刚提交的预约。

> **教训：serialize 之后必须用当前读（`FOR UPDATE`）才能看到最新已提交数据。**
> 锁解决的是「执行顺序」，快照解决的却是「能看到什么」，两者缺一不可。

### 验证

- 冒烟用例：容量压到 1 → 6 并发抢同一时段 → **恰好 1 单成功、5 单 409**
- pytest 用例：容量压到 2 → **10 并发 → 恰好 2 单成功**，并核对数据库实存单数等于容量

## 五、RAG 洗护安全知识库

### 5.1 数据从哪来

| 来源 | 数量 | 位置 | 维护方式 |
|---|---|---|---|
| 内置短条目 | 12 条 | `app/services/knowledge_service.py`（`SEED_KNOWLEDGE`） | 改代码 + `init_db` |
| 门店知识文档 | **5 篇** | `backend/data/knowledge/*.md`（front matter + 正文） | 直接改 markdown，重新索引即可 |

5 篇文档覆盖：洗护前皮肤检查、产品成分与过敏原、应激分级与安抚、药浴/驱虫/疫苗间隔、
老年与特殊体型操作规范。**按篇入库、不做切块** —— 门店规范一篇就是一个语义单元，
切碎反而丢上下文。

`knowledge_entry` 字段：`category` + `title` + `content` + `tags`（与规则引擎 `risk_key` 对齐）
+ `keywords` + `species` + `source`（来源可追溯）。

### 5.2 向量库（LlamaIndex + Chroma，V8.4）

```
backend/data/knowledge/*.md ──┐
                              ├──> knowledge_entry(MySQL) ──> LlamaIndex ──> Chroma(持久化)
SEED_KNOWLEDGE(代码) ─────────┘         │                    （SentenceSplitter 切块 + 向量检索 + rerank）
                                        └── risk_report.knowledge_refs（标签打分，不走向量）
```

写法对齐参考项目 `RAG知识库聊天系统`：`DashScopeEmbedding` → `SentenceSplitter` → `VectorStoreIndex`
→ `ChromaVectorStore`，**只保留基础 RAG**（不做 HyDE、不做 BM25 混合、不做 CRAG/GraphRAG）。

- **切块**：先按 `## ` 小节预切，再交给 `SentenceSplitter(chunk_size=500, chunk_overlap=50)`
  处理超长小节 —— 17 条知识 → **36 个 chunk**。只按字数硬切会把「耳后小面积试洗」这类小段落
  和别的内容混在一段里，出现「文档对了、段落错了」；
- **embedding**：主 `text-embedding-v4`（336ms / 1024 维）→ 备 `qwen3.7-text-embedding`（742ms）；
  均不可用时用**本地哈希向量**，最终兜底是标签打分；
- **rerank（可选）**：`qwen3-rerank` / `qwen3-vl-rerank` / `gte-rerank-v2` 实测均可用（0.3~0.6s），
  默认开 `RERANK_ENABLED=true`；失败时保持向量顺序，不影响回答；
- **建索引**：`python scripts/index_knowledge.py`（幂等，全量重建）；`init_db` 灌完知识也自动重建；
- **条目数变化自动重建**：`ensure_index()` 比对条数，不一致就重建；
- **collection 名带 embedding 后缀**（`knowledge_text_embedding_v4`），不同模型的向量永不混查。

### 5.3 降级链（硬要求）

| 层级 | 条件 | 行为 |
|---|---|---|
| 1 | LlamaIndex + 百炼 embedding 正常 | 向量召回 + rerank，`matched` 显示「重排相关度 0.xx」 |
| 2 | embedding 全部不可用 | 退回本地哈希向量（字面相似度），仍能检索 |
| 3 | 索引建不起来 / 依赖缺失 | 标签与关键词打分（`_score_entries`） |

> 实测踩坑：`DashScopeEmbedding` 默认 `embed_batch_size=100`，而百炼 embedding 单次最多 10 条，
> 超了不报错、直接返回**全 None 的向量**。代码里已固定 `embed_batch_size=10`。

> **索引新鲜度（V8.4.4）**：建索引时会把「知识条目数 / 块数」写进 Chroma collection 元数据；
> 每次检索前比一次数据库条目数，不一致就自动重建 —— 新增/修改 `data/knowledge/*.md`
> **无需重启服务、也不用手动跑索引脚本**（前提是文档已 seed 进 `knowledge_entry`）。
> 另外检索结果带**相关度阈值**（rerank 0.45 / 向量 0.30），低分块不再塞进答案；
> 回答标题会带命中**小节**（「文档 · 四、什么时候改用免水洗」），便于判断依据。

### 5.4 两个使用方

1. **风险报告**（`assess_risk`）：规则命中项 `risk_key` 与 `tags` 对齐打分 → 注入 LLM 提示词
   （`RISK_USER_TEMPLATE` 的知识段落）+ 写入 `risk_report.knowledge_refs`。
   这条链路**不依赖向量库**，保证下单主链路少一个失败点。
2. **Agent 对话**（`search_knowledge` 工具，**RAG 的唯一对外入口**）：
   用户在对话里问「怎么洗 / 能洗吗 / 多久能洗澡 / 注意什么」，Agent 在对话链路内自主调用
   `search_by_query` → LlamaIndex 检索 → rerank；回答里带条目标题、命中段落、`依据` 与 `来源`，
   片段另以 `refs` 事件下发前端折叠展示。

> **没有独立的知识检索页面。** 检索是 Agent 的一个工具，由 Agent 判断是否需要才调用。
> 知识库管理页只做文档治理（上传 / 切块 / 任务状态 / 删除 / 重建）。
> 理由：检索的价值是支撑回答，脱离回答单独搜一段文本，用户拿不到结论，还多一份要维护的入口。

### 5.5 管理页面、权限与接口（V8.5）

门店端新增 `/staff/knowledge`：店员与店长共用同一页面，但后端权限守卫不同。

- **店员**：查看文档、查看可追溯切块、查看处理任务（**检索通过对话进行，页面不设搜索框**）；
- **店长**：包含全部店员能力，另可批量上传、删除文档、手工重建索引；
- **宠主**：所有知识库管理接口均返回 403。

管理接口：

- `GET /api/v1/knowledge/meta`：统计、集中配置、当前角色权限；
- `GET /api/v1/knowledge/documents`：分页查看文档；
- `POST /api/v1/knowledge/documents/upload`：店长批量上传（multipart）；
- `GET /api/v1/knowledge/documents/{id}/chunks`：查看切块和页码/段落/字符区间；
- `DELETE /api/v1/knowledge/documents/{id}`：店长删除文档并自动排队重建索引；
- `GET /api/v1/knowledge/tasks`、`GET /api/v1/knowledge/tasks/{id}`：轮询任务状态；
- `POST /api/v1/knowledge/index/rebuild`：店长手工重建；
- `POST /api/v1/knowledge/search`：**服务层内部接口**，供 Agent 工具与风险链路调用，前端页面不接入。

上传支持 PDF、DOCX、TXT、Markdown，默认单文件 20MB、单次 5 个。文件先做扩展名、大小、空文件校验，
再用 SHA-256 识别重复内容；上传进度由 Axios `onUploadProgress` 提供。原始文件保存在
`data/knowledge_uploads`，**不挂到 `/static`**，避免未登录访问门店内部资料。

切块支持 `fixed / paragraph / heading` 三种策略，块大小与重叠长度可配；PDF 保留页码，
Word/TXT/Markdown 保留段落位置，同时记录字符起止和小节标题。上传文档已经切好的块直接写入 Chroma，
不会再被默认的 `SentenceSplitter(500/50)` 二次切碎。

异步任务使用独立的 `knowledge_ingest_task` 表记录 `pending / processing / completed / failed`、
进度与错误原因；进程内并发上限默认 2，索引写入另加串行锁。服务重启会重新排队未完成任务。
这是单机可靠队列；多实例部署时应替换成 arq/Celery/Redis 队列。

关键配置集中在 `.env`：`KB_UPLOAD_DIR`、`KB_ALLOWED_EXTENSIONS`、`KB_MAX_FILE_MB`、
`KB_MAX_BATCH_FILES`、`KB_DEFAULT_CHUNK_STRATEGY`、`KB_DEFAULT_CHUNK_SIZE`、
`KB_DEFAULT_CHUNK_OVERLAP`、`KB_MIN_CHUNK_SIZE`、`KB_MAX_CHUNK_SIZE`、
`KB_MAX_CHUNK_OVERLAP`、`KB_MAX_CONCURRENT_TASKS`。

### 5.6 数据模型（V8.5）

- `knowledge_document`：原文件名、类型、MIME、大小、SHA-256、受保护存储路径、上传人、切块配置、状态与失败原因；
- `knowledge_chunk`：文档内序号、正文、小节标题、页码/段落/字符区间、来源追溯文案；
- `knowledge_ingest_task`：入库/重建任务、进度、阶段说明、失败原因、开始/结束时间；
- `knowledge_entry`：继续保存内置短条目与随代码维护的 Markdown 规范，风险报告的规则兜底不受上传链路影响。

### 5.7 合规与边界

知识条目由门店自行维护，**不抓取、不镜像第三方受版权保护的内容**；风险报告固定附带免责声明，
不构成医疗诊断。索引是单机文件（多实例部署时每个实例各自索引一份，见 docs/09 已知限制）。

## 六、意图识别评测集（`scripts/eval_intent.py`）

### 为什么需要

架构上「LLM 不可用时降级到规则法」是硬要求，但**降级会损失多少准确率**此前从未量化。

### 方法

42 条样本覆盖三角色、每类意图 2 种问法（含闲聊负样本），分别跑：
- **规则法**：`AgentRunner._interpret_by_rule`（LLM 不可用时的真实降级路径）
- **LLM 法**：生产提示词 + 角色工具画像，逐条调用

### 结果（实测）

| 阶段 | 规则法准确率 | 说明 |
|---|---|---|
| 首次评测（口径有误 + 规则缺陷） | 52.4% | —— |
| 修正评测口径后 | 78.6% | 规则法必须走完整链路，只调运营意图方法会漏掉宠主全部意图 |
| **补强规则关键词后** | **100%（42/42）** | 见下方修复清单 |
| LLM 法（qwen-flash） | 100%（42/42） | **降级代价 0 个百分点** |

### 评测驱动出的 5 处真实规则缺陷

1. **写配置被只读意图抢占**：「把流失预警天数从 90 改成 60」被判为「查流失预警」——
   口语化的「把 X 改成 Y」通常不含「配置」二字，写操作判定必须**提前到只读意图之前**；
2. **疑问句被当成下单**：「明天还有哪些时段可以预约？」因含「预约」被判为创建预约 ——
   需让疑问句式（哪些 / 还有空 / 几点）优先；
3. **「我还有几单没洗」被判为查时段**：「还有」过于宽泛，改为「还有空 / 还有位置」，
   并让「我的预约」类判定优先；
4. **「帮**给**客户预约」漏识别**：代客预约关键词缺「给客户预约 / 为客户预约」；
5. **「把 liu 这个账号停用」漏识别**：启停账号改为「账号 + 启停动词」的组合判定，而非固定短语。

> 同时修掉了一处**我自己引入的回归**：「最近谁改过门店配置」被新加的配置判定抢先命中，
> 已把「门店配置只读」判定移到店长专属意图之后（它属于审计，不是查配置）。
> 这也说明：**规则法的判定顺序和关键词同等重要，顺序错了会制造新 bug。**

**用法**：
```bash
python scripts/eval_intent.py            # 规则法 + LLM 法（消耗免费额度）
python scripts/eval_intent.py --no-llm   # 只跑规则法（零消耗，可进 CI）
```

**已知限制**（不做模糊表述）：
- 调度器为进程内实现，**水平扩展时任务不会分摊**（由行锁保证不重复执行，但没有负载均衡）；
  任务量增长后建议切 arq（业务代码无需改动）；
- `slot_lock` 只锁「日期 + 时段」，「同宠物同日重复预约」仍是软约束（不同时段不冲突），
  由 `_check_duplicate` 尽力拦截 —— 影响面小，故未加第二把锁；
- 评测集为自建回归基线，**不等于真实场景准确率**，用途是防止后续改动引入回退；
- 知识库入库任务目前是**单机进程内异步 worker + MySQL 状态表**；进程重启可恢复，
  但多实例不会做任务认领和分摊，水平扩展前必须换 arq/Celery/Redis 队列。
