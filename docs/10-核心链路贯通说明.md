# 十条核心链路：从前端到后端（逐个文件、逐个函数）

> 目的：接手项目时，先按这十条把「一次用户动作怎么穿过前后端」走一遍，比读目录更快建立全貌。
> 每条都标注了**具体文件 → 具体函数/接口 → 具体服务方法**，可对照代码逐个打开。
> 读之前建议先看 `README.md` 的「2.4 一次请求穿过哪些层」。

---

## 1. 登录：账号密码 → 双令牌 → 按角色落地

| 层 | 位置 |
|---|---|
| 前端页面 | `frontend/src/views/login/index.vue` → `doLogin()` |
| 前端接口 | `frontend/src/api/auth.ts` → `authApi.login()` |
| 请求封装 | `frontend/src/api/request.ts` → 请求拦截器注入 `Authorization` 头 |
| 状态 | `frontend/src/stores/user.ts` → `setAuth()`（写 token + 用户信息） |
| 路由 | `frontend/src/router/index.ts` → 登录成功后按 `role` 跳 `/user/home` 或 `/staff/home` |
| 后端路由 | `backend/app/routers/auth.py` → `login()`（`POST /api/v1/auth/login`） |
| 后端服务 | `backend/app/services/auth_service.py` → `authenticate()` 校验账密 → `issue_tokens()` 签发 JWT |
| 数据表 | `user`（读取账号、比对密码哈希） |
| 审计 | `auth_service.login()` 内 `write_log` 记录登录行为 |

**关键点**：密码错误统一抛 `BizError(4011)`，不区分「用户名不存在」和「密码错」，避免暴露账号是否存在。

## 2. 令牌过期：401 静默续期，并发请求排队重放

| 层 | 位置 |
|---|---|
| 前端拦截 | `frontend/src/api/request.ts` → 第 81 行起的「401 静默续期」逻辑 |
| 前端接口 | `api/auth.ts` → `authApi.refresh()` |
| 后端路由 | `backend/app/routers/auth.py` → `refresh()`（`POST /api/v1/auth/refresh`） |

**链路**：业务请求返回 401 → 拦截器**只发一次** `refresh` 请求 → 拿到新 access token 后，把排队等着的失败请求**自动重放** → 用户完全无感；若 refresh 也失败（401/过期），才清空 token 跳登录页。

**关键点**：这是「队列化重放」而不是「每个请求各自刷新」——否则 5 个并发请求会打出 5 次刷新，把 refresh 令牌的轮换机制打乱。

## 3. 宠主提交预约（表单入口）

| 层 | 位置 |
|---|---|
| 前端页面 | `frontend/src/views/user/AppointmentCreate.vue` → `loadSlots()`（拉时段）、`submit()`（提交） |
| 前端接口 | `frontend/src/api/appointment.ts` → `appointmentApi.slots()` / `create()` |
| 后端路由 | `backend/app/routers/appointment.py` → `slots()`（`GET /appointments/slots`）、`create_appointment()`（`POST /appointments`，summary「宠主提交预约（表单入口）」） |
| 后端服务 | `backend/app/services/appointment_service.py` → `create_by_customer()` |
| 内部步骤 | `_validate_date()`（日期与时段合法性）→ `_lock_slot()`（时段行锁）→ `_check_capacity()`（**当前读**统计占用）→ `_check_duplicate()`（同日重复拦截）→ `risk_service.assess_risk()` → 落库 |
| 数据表 | `appointment`、`risk_report`、`operation_log`（审计）、`message`（通知宠主） |

**关键点**：`submit()` 会带 `idempotent_key`（前端生成），重复提交返回**同一单**而不是两笔；这是「表单入口」与「AI 入口」共用的同一服务方法。

## 4. AI 对话：一句「明天有哪些时段」走到只读工具

| 层 | 位置 |
|---|---|
| 前端页面 | `frontend/src/views/chat/index.vue` → `sendText()` 发送，`handleEvent()` 处理 SSE 事件 |
| 前端接口 | `frontend/src/api/chat.ts` → `chatApi.sendMessage()`（**fetch + ReadableStream**，因为 EventSource 不支持 POST 和自定义头） |
| 后端路由 | `backend/app/routers/chat.py` → `send_message()`（`POST /chat/message`，SSE） |
| 会话锁 | `backend/app/services/session_lock.py` → `acquire()`（同一会话并发消息串行） |
| Agent 内核 | `backend/app/agent/react.py` → `AgentRunner.stream()`（路由调度 Agent 的执行器） |
| 路由分发 | `react.py` → `_interpret()`：先跑 `_interpret_by_rule()` 兜底，LLM 可用时再纠偏；判定意图后分派给「门店业务 Agent」 |
| LLM 客户端 | `backend/app/agent/llm/client.py` → `chat_with_fallback()`（模型链依次尝试） |
| 工具执行 | `backend/app/agent/tools/registry.py` → `query_slots()`（门店业务 Agent 的只读工具） |
| 业务服务 | `appointment_service` / `setting_service.get_int("default_slot_capacity")` |
| 数据表 | `appointment`、`store_setting` |

**返回**：SSE 依次推 `meta → intent → thought → action → observation → answer(delta) → done/end`，前端 `handleEvent()` 按 `type` 分别渲染思考链、工具胶囊和逐字回答。

**关键点**：LLM 任何异常都降级到 `_interpret_by_rule()` —— AI 不可用不影响查时段（这条链路在 `scripts/chaos_test.py` 里被强制验证）。

## 5. AI 对话：写操作的二次确认闸门

| 层 | 位置 |
|---|---|
| 前端 | `views/chat/index.vue` → `handleEvent()` 的 `case 'confirm'`：渲染确认卡（复述单号/宠物/日期），**用户点确认前不落库** |
| 后端入口 | `routers/chat.py` → `send_message()`（用户回复「确认」再次进入同一条链路） |
| 待确认处理 | `react.py` → `_handle_pending()` → `is_confirm()` 判定确认 → `_execute_and_reply()`（仍由门店业务 Agent 执行） |
| 合规校验 | 合规风控 Agent 与业务 Agent 并行跑一遍：急症 / 处方 / 偏方命中即改写出口 |
| 工具层 | `tools/registry.py` → `create_appointment()`（`@tool(..., write=True)`） |
| 业务服务 | 与第 3 条**同一个** `appointment_service.create_by_customer()` |
| 审计 | `audit_service.write_log`，`source` 标记为对话入口 |

**关键点**：LLM 只产出「意图 + 槽位」，**从不直接写库**；真正落库走与表单相同的 Service 方法和幂等键，因此「AI 下的单」和「表单下的单」在审计里可区分、在业务上等价。

## 6. 寄养下单：三重定价 + 疫苗硬门槛

| 层 | 位置 |
|---|---|
| 前端页面 | `frontend/src/views/user/BoardingCreate.vue` → `loadRooms()`（房态）、`refreshQuote()`（报价）、`submit()` |
| 前端接口 | `frontend/src/api/boarding.ts` → `boardingApi.rooms()` / `quote()` / `createOrder()` |
| 后端路由 | `backend/app/routers/boarding.py` → `create_order()`（`POST /boarding/orders`） |
| 后端服务 | `backend/app/services/boarding_service.py` → `create_order()` |
| 内部步骤 | `_check_vaccine()`（**入住当天疫苗仍有效**，硬门槛）→ `_lock_room_and_check()`（锁房舍行 + 当前读统计重叠订单）→ `quote()`（体重档 × 房型系数 × 节假日系数，逐晚计价）→ 落库 + 生成照护计划与接送任务 |
| 数据表 | `boarding_room`、`boarding_order`、`boarding_care_plan`、`boarding_pickup_task`、`message` |

**关键点**：日期一变，前端 `watch(dateRange)` 触发 `loadRooms()` + `refreshQuote()` —— 这里刻意**不用** `el-date-picker` 的 `@change`（实测该事件在区间模式下可能不触发，详见 `docs/01` E-39）。

## 7. 用品下单：过敏原 × 宠物档案硬拦截，库存防超卖

| 层 | 位置 |
|---|---|
| 前端页面 | `frontend/src/views/user/Goods.vue` → `openDetail()`（详情 + 冲突原因）、`addToCart()`、`submitOrder()` |
| 前端接口 | `frontend/src/api/goods.ts` → `goodsApi.products()` / `addCart()` / `createOrder()` |
| 后端路由 | `backend/app/routers/goods.py` → `create_order()`（`POST /goods/orders`） |
| 后端服务 | `backend/app/services/goods_service.py` → `create_order()` |
| 内部步骤 | `safety_conflicts()`（过敏原/禁忌/月龄/体重比对，命中即**硬拦截**）→ `_load_sku(lock=True)`（`FOR UPDATE` + **`populate_existing`**）→ `_deduct_stock()` 扣库存 → 生成 `pickup_code`（8 位核销码）→ 清购物车 |
| 数据表 | `product`、`product_sku`、`cart_item`、`goods_order`、`goods_order_item`（价格快照） |

**关键点**：`_load_sku` 的锁行必须带 `populate_existing=True`，否则 SQLAlchemy 的 identity map 会返回会话里缓存的旧对象，`stock` 还是旧值 —— V7.2 实测 4 并发 4 单全成功才发现（`docs/01` E-35）。

## 8. 宠物实景：凭证 → MJPEG 拉流，门店端推帧

| 层 | 位置 |
|---|---|
| 前端（看） | `frontend/src/views/user/Camera.vue` → `watch()` 申请凭证、`startCountdown()` 倒计时、`snap()` 抓拍 |
| 前端接口 | `frontend/src/api/camera.ts` → `cameraApi.openSession()`、`cameraStreamUrl(token)` |
| 前端（推） | `frontend/src/views/staff/Camera.vue` → `pushFrame()`（canvas 抓帧后 **fetch** 直推，见第 207 行） |
| 后端路由 | `backend/app/routers/camera.py` → `create_session()`（`POST /camera/sessions`）、`stream()`（`GET /camera/stream/{token}`）、`push_frame()`（`POST /camera/frames/{token}`） |
| 后端服务 | `backend/app/services/camera_service.py` → `issue_token()`（隐私红线全在此校验）、`mjpeg_stream()`、`push_frame()` |
| 内存缓存 | `camera_service` 内的 `FrameHub`（`put/get/drop`）——**实时流不落盘** |
| 数据表 | `camera_device`、`camera_session`（观看留痕）、`camera_snapshot` |

**红线**（`issue_token` 内逐条校验）：只能看自己的、只能在住期间、设备必须在线、必须在观看时段内、单订单并发路数受限、凭证短期有效。`<img>` 带不了 Authorization 头，所以拉流用 token 鉴权而非 JWT。

## 10. 店长改配置 → 立即影响预约容量与 SLA

| 层 | 位置 |
|---|---|
| 前端页面 | `frontend/src/views/staff/Settings.vue` → 保存单项配置 |
| 前端接口 | `frontend/src/api/setting.ts` → `settingApi.update()` |
| 后端路由 | `backend/app/routers/store_setting.py` → `update_setting()` |
| 后端服务 | `backend/app/services/setting_service.py` → `update_setting()` |
| 规则来源 | `backend/app/constants/enums.py` → `SETTING_RULES`（类型 + 取值范围，单一事实来源） |
| 数据表 | `store_setting` |
| 下游生效 | ① `appointment_service._check_capacity()` 读 `default_slot_capacity`；② `boarding_service.quote()` 读 `board_price_*`；③ `appointment_service.sla_scan()` 读 `staff_confirm_timeout_hours` / `auto_cancel_on_timeout` |

**关键点**：`update_setting()` **只 flush 不 commit**，提交由路由负责；测试或脚本直接调它必须自己 `commit()`，否则会出现「改了没生效但用例全绿」的假通过（`docs/01` E-45）。

## 附：怎么用这份文档

1. 想改某个功能，先在表里找到它的「前端页面 → 后端服务」两个端点，从这两头往中间读；
2. 想加新接口，照第 3 条的样子补齐七处（页面函数、api 方法、路由、服务、表、审计、消息）；
3. 想确认某条链路没被改坏，跑对应的验证：`backend/scripts/smoke_test.py`（接口契约）、
   `tests/test_services_*.py`（服务层规则）、`scripts/chaos_test.py`（降级）、
   `frontend/scripts/verify-spa.mjs`（真实浏览器）。
