## 2026-10-14 · V1 初始化

### E-01 pip 安装依赖报 `No matching distribution found`（from versions: none）

- **现象**：`pip install -r requirements.txt -i https://pypi.tuna.tsinghua.edu.cn/simple` 全部包报
  `Could not find a version that satisfies the requirement ... (from versions: none)`，
  但 `curl` 访问该镜像返回 200。
- **根因**：当前网络环境下 pip 进程无法正常访问该镜像索引（代理/沙箱层面拦截），并非包不存在。
- **修复**：改用默认 PyPI 源安装；同时把 `requirements.txt` 从精确区间锁定
  （`fastapi>=0.115,<0.116`）改为最小版本约束（`fastapi>=0.115`），避免因索引可用版本差异导致解析失败。
- **预防**：V5 阶段执行依赖冒烟 Spike 后，输出 `requirements.lock.txt`（`==` 冻结），
  并在 README 中同时给出「默认源」与「内网镜像源」两套安装命令。

### E-02 `ImportError: cannot import name 'RISK_LEVEL_LABEL' from 'app.constants'`

- **现象**：`app/services/appointment_service.py` 导入常量失败，应用无法启动。
- **根因**：常量集中定义在 `app/constants/enums.py`，但包出口文件 `app/constants/__init__.py`
  只挑选了部分名字再导出，新增的 `RISK_LEVEL_LABEL / MESSAGE_TYPE_LABEL / ROLE_LABEL` 漏加。
- **修复**：重写 `app/constants/__init__.py`，把全部对外常量显式导出，并补充
  `SETTING_RULES / VALID_ORDER_STATUS / TERMINATE_REQUIRED_STATUS / SERVICE_PRICE_HINT` 等。
- **预防**：新增常量时必须同步更新包出口；常量只有一个事实来源（`enums.py`），业务代码只从 `app.constants` 导入。

### E-03 `ImportError: cannot import name 'get_owned_pet' from 'app.services.pet_service'`

- **现象**：`app/services/__init__.py` 导入失败。
- **根因**：包出口文件是按「设计稿函数名」写的，实现时函数被命名为 `get_pet_or_404`，两者不一致。
- **修复**：把 `app/services/__init__.py` 的导出清单改为与实现完全一致的函数名，
  并补齐 `auth_service / stats_service / risk_service` 的导出。
- **预防**：包出口文件必须与实现同一次提交内同步；避免「先写出口再写实现」。

### E-04 `RuntimeError: Event loop is closed` / `MissingGreenlet`（TestClient 场景）

- **现象**：冒烟测试用 `TestClient(app)` 逐次发请求，第一个请求正常，后续请求抛
  `AttributeError: 'NoneType' object has no attribute 'send'`，退出时刷出
  `RuntimeError: Event loop is closed`。
- **根因**：未使用上下文管理器的 `TestClient` 每次请求都会新建一个事件循环，
  而 SQLAlchemy 的 `AsyncEngine` 连接池是模块级单例，连接在循环 A 创建后被循环 B 复用。
- **修复**：冒烟脚本改为 `with TestClient(app) as client:`，让 lifespan 与全部请求复用同一个事件循环。
- **预防**：任何涉及 async 引擎的测试脚本都必须用 `with TestClient(...)`；生产环境用 uvicorn 单循环不受影响。

### E-05 `MissingGreenlet: greenlet_spawn has not been called`（序列化 ORM 对象时）

- **现象**：`POST /api/v1/pets` 创建成功后返回数据时抛 `MissingGreenlet`，日志报
  `greenlet_spawn has not been called; can't call await_() here. Was IO attempted in an unexpected place?`
- **根因**：`TimestampMixin` 的 `created_at / updated_at` 只设置了 `server_default=func.now()`，
  没有 Python 侧 `default`。INSERT 后这两个属性在 ORM 中处于「未加载」状态，
  而 `pet_to_out()` 是**同步函数**，在 `await` 上下文之外访问该属性会触发惰性加载（发起 SQL），
  但此时没有 SQLAlchemy greenlet 上下文 → 报错。
- **修复**：`server_default` 之外补上 `default=datetime.now` / `onupdate=datetime.now`，
  让值在 Python 侧生成并随 INSERT 一起写库，属性天然可用。
- **预防**：async ORM 三条纪律 ——
  ① 时间戳等默认值一律给 Python 侧 default；
  ② 序列化前不依赖惰性加载，必要时显式 `await db.refresh(obj)`；
  ③ 关联对象用 `selectinload/joinedload` 预加载，不在同步转换函数里触碰未加载关系。

### E-06 `pymysql.err.ProgrammingError (1064) ... near 'NULLS FIRST'`

- **现象**：报表接口 `GET /api/v1/report/summary` 500，SQL 报语法错误。
- **根因**：流失预警查询用了 SQLAlchemy 的 `.nullsfirst()`，MySQL 不支持标准 SQL 的
  `NULLS FIRST / NULLS LAST` 语法。
- **修复**：去掉 `.nullsfirst()`，改为 `.order_by(col.asc())` —— MySQL 的 ASC 排序本身把 NULL 排在最前，语义等价。
- **预防**：跨方言 SQL 只使用 MySQL 已支持语法；写聚合/排序前先确认目标方言能力。

### E-07 冒烟用例「宠主查看他人宠物被拒绝」误报失败

- **现象**：用例期望 403，实际返回 200。
- **根因**：测试数据取的是 `/pets` 列表下标 2 的元素 —— 而宠主视角的列表**只返回自己的宠物**，
  创建冒烟宠物后下标漂移，取到的仍是自己的宠物，等于在测「访问自己宠物」，必然 200。
- **修复**：改用**店员视角**拉取全量宠物，筛出 `user_id != 当前用户` 的宠物再断言 403，
  并补充「宠主修改他人宠物也被拒绝」用例。
- **预防**：越权用例的被测对象必须来自「与我无权关系」的数据源（管理员/店员视角或直接查库），
  不能从被限制后的列表里取。

### E-08 `pet_service.list_pets` 残留无效分支

- **现象**：代码审查发现 `cond.append(...) if False else None` 这类无效语句（原意为预留店员过滤）。
- **根因**：先写占位后忘了删除；店员档案的归属过滤最终在 `assert_can_access/assert_can_edit` 中实现。
- **修复**：删除无效分支，保持「宠主看自己的、店员/店长看全部 + 归属校验」的明确语义。
- **预防**：提交前跑一遍自查清单，禁止提交含 `if False`、`pass  # TODO` 的占位实现。

### E-09 `NameError: name 'settings' is not defined`（LLM 增强分支）

- **现象**：启用 LLM 后，创建预约调用 `assess_risk` 抛 `NameError`，预约接口 500。
- **根因**：`risk_service` 重构时新增了 `settings.llm_available` 判断，但模块顶部未导入 `app.config.settings`
  （原实现里 `settings` 只在函数内局部导入，改成模块级使用时漏了顶层导入）。
- **修复**：在 `risk_service` 顶部补 `from app.config import settings`，并把原先函数内的局部导入上提、
  把 `birthday` 月龄计算统一改成复用 `utils.calc_age_month`，消除重复实现。
- **预防**：函数内局部 import 是隐患温床；同一模块反复用的依赖必须放在模块顶部，
  局部 import 仅用于「打破循环依赖」这一种场景。

### E-10 百炼 `qwen-turbo` 返回 HTTP 429（You have exceeded your current request limit）

- **现象**：免费模型链探测时 `qwen-turbo` 连续两次 429，其余模型正常。
- **根因**：该模型已不在当前免费额度范围内 / 请求限额已耗尽（官方活动调整）。
- **修复**：把 `qwen-turbo` 从默认免费模型链移除，默认链改为
  `qwen-flash → qwen3.7-flash → qwen-plus`（三者实测均可用，见 `docs/04`）。
  同时**不把型号硬编码**，全部通过 `.env` 的 `LLM_MODEL / LLM_FALLBACK_MODELS` 配置，
  控制台清单变化时只改配置。
- **预防**：凡是「平台侧可变」的枚举（模型名、限额、端点），一律配置化 + 提供探测脚本；
  对 429 不做无限重试（`LLM_MAX_RETRIES=1`），避免额度被异常放大消耗。

### E-11 冒烟用例「风险预约创建」在全新数据库上偶发 409

- **现象**：`--reset` 后重跑冒烟测试，风险用例返回 409「该宠物当天已存在有效预约」。
- **根因**：用例用 `pets[2]` 兜底到 `pets[0]`，导致与前面已创建的预约**同宠物同日**，
  被去重规则正确拦截 —— 是**用例数据准备有误**，不是业务缺陷。
  （此前因数据库里累积了历次测试遗留宠物，下标漂移才「碰巧」没触发。）
- **修复**：改用另一位宠主（`liu`）的宠物「旺财」（档案含攻击倾向 / 皮肤病 / 过敏史，必命中高风险），
  并改用独立日期；顺带补充「宠主无法查看他人预约（403）」用例。用例数 37 → 39。
- **预防**：用例之间不得共享「同宠物 + 同日」这类受限资源；
  受限资源的测试数据必须来自独立维度（不同用户 / 不同日期）。

### E-12 初始化脚本灌演示数据耗时数分钟（每条预约都打 LLM）

- **现象**：启用 LLM 后执行 `python scripts/init_db.py --reset`，79 条演示预约每条都触发一次
  风险摘要 LLM 调用，整体耗时从 **4.7 秒膨胀到数分钟**，命令一度超时被中断。
- **根因**：`assess_risk()` 默认按 `settings.llm_available` 决定是否走 LLM，
  而演示数据是**批量生成**的，逐条调用外部 API 属于典型的批处理反模式。
- **修复**：灌数据的两处循环显式传入 `use_llm=False`（走规则引擎），
  仅保留 1 条高风险示例预约走 LLM，用于演示 AI 增强效果。耗时回到 **4.7 秒**。
- **预防**：**批处理路径禁止默认调用外部 API**。凡是循环内可能触发的网络调用，
  必须提供显式开关，并在批处理场景下关闭；单条链路保留 AI 能力即可。

### E-13 确认词匹配过宽导致「问句里的可以」被当成确认

- **现象**：会话残留了一条待确认的取消动作，用户下一句问「明天还有哪些时段**可以**预约？」，
  系统直接把它当成确认并执行了取消，返回「没有找到单号」。
- **根因**：`_handle_pending()` 用 `any(w in text for w in CONFIRM_WORDS)` 判断，
  而「可以」既是确认词也是中文里极常见的副词 → 误判。
- **修复**：改用整串正则 `^(确认|确定|好的|可以|…)[呀吧哦～]?$` 且限制长度 ≤ 8，只有「整句就是这个意思」才生效；
  取消同理。同时把冒烟测试改为使用**独立会话**，避免用例之间共享 `pending_action` 状态。
- **预防**：NLU 判定不要用「子串包含」表达意图；短句判定必须做**整串匹配 + 长度约束**。

### E-14 身份证脱敏正则过宽，把 18 位预约单号打成星号

- **现象**：AI 助手的回复落库后，预约单号变成 `PG202610********6033`，用户看不懂自己的单号。
- **根因**：日志脱敏用了 `(?<!\d)(\d{6})\d{8}(\d{4})(?!\d)`，
  而预约单号是「PG + 14 位时间戳 + 4 位随机数」= 恰好 18 位数字，被当成身份证号脱敏。
- **修复**：
  1. 身份证正则收紧为**中国身份证真实结构**（6 位地区 + 出生日期 + 3 位顺序 + 校验位），逻辑上不会再命中单号；
  2. `chat_message` 入库时**只对用户输入脱敏**，助手回复原文入库（含单号等业务标识）；
  3. 冒烟测试新增 3 条脱敏回归用例（单号不脱敏 / 手机号脱敏 / 身份证脱敏）。
- **预防**：脱敏正则必须锚定目标数据的**真实格式**，不能只用「长度 + 数字」特征；
  脱敏只应作用于**日志与用户输入**，不应破坏业务标识的可读性。

### E-15 Vue 模板中 `v-if="expr as alias"` 不被支持

- **现象**：`vue-tsc` 报 `Cannot find name 's'` 与 `Property 's' does not exist on ...`。
- **根因**：在 `v-if="slotOf(day, slotTime) as s"` 里使用了 TS 的类型断言语法当作变量别名，模板编译器不支持。
- **修复**：把「多重查找 + 计算」提前到 `rows` 计算属性中预计算（行 = 时段，单元格 = 日期 × 时段 + 占用 + 样式类），
  模板只做纯渲染。既解决类型问题，也消除了模板内 O(n²) 重复查找。
- **预防**：Vue 模板只做渲染，不做查找与计算；复杂派生数据一律在 `computed` 中预计算。

### E-16 ECharts 配置对象字面量被推断为宽泛 `string` 类型

- **现象**：`vue-tsc` 报 `Type 'string' is not assignable to type '"category"'`，涉及 `type` / `trigger` 等字段。
- **根因**：`computed(() => ({...}))` 的返回对象没有上下文类型，字面量被推断为 `string` 而非字面量联合类型，
  与 `EChartsOption` 不兼容。
- **修复**：写成 `computed<EChartsOption>(() => ({...}))`，让 TS 按目标类型做上下文类型化。
- **预防**：凡是「返回值要符合某个复杂外部类型」的 `computed`，都显式标注泛型，而不是依赖推断。

### E-17 中文 CSV 文件名在下载时乱码

- **现象**：导出文件名中的中文（如「经营概览」）在部分浏览器下变成乱码或被截断。
- **根因**：`Content-Disposition` 直接使用 `filename="中文.csv"`，非 ASCII 字符不符合 HTTP 头规范。
- **修复**：后端改为 `filename*=UTF-8''<percent-encoded>`；前端从响应头解析该形式并回退到普通 `filename`，
  同时 CSV 内容加 UTF-8 BOM，保证 Excel 双击不乱码。
- **预防**：所有下载类接口统一走「RFC 5987 编码 + BOM」这套组合，前端统一用 `parseFilename()` 解析。

## 2026-10-15 · V5（多角色 Agent）与 UI 微调

> V5 把 Agent 能力扩展到店员端与店长端。这批问题里有 **2 个是「阻塞级 / 安全级」**，
> 而且都不是新功能写错，而是**既有代码在新用法下暴露出来的**，很值得记。

### E-18 代客预约在「宠物没有档案」时必然 422（阻塞级）

- **现象**：店员代客下单、客户还没建档时，前端传 `pet_id: 0` 被 422 拒绝；不传 `pet_id` 又报「该字段必填」。
  **也就是说「代客预约 + 临时建档」这条店员核心链路根本走不通。**
- **根因**：`StaffAppointmentCreate` 继承了 `AppointmentCreate` 的 `pet_id: int = Field(gt=0)`（必填且 >0），
  而服务层 `create_by_staff` 是按「pet_id 可选、缺省时用 `pet_name` 临时建档」实现的 —— **契约与实现不一致**。
- **修复**：子类把 `pet_id` 覆写为可选（`None`），并用 `model_validator` 强制「`pet_id` 与 `pet_name` 至少给一个」。
- **预防**：继承式 Schema 覆写字段时，必须回到服务层确认真实契约；**「必填」与「可选」的分歧只会在
  边界场景（无档案）暴露**，常规用例全绿也发现不了。

### E-19 新增的写工具绕过了二次确认闸门（安全级）

- **现象**：V5 新增的 `advance_appointment`（推进订单状态）**没有出确认卡，直接改了库**。
- **根因**：确认闸门由硬编码集合把关：`WRITE_INTENTS = {"create_appointment", "cancel_appointment", "reschedule_appointment"}`。
  新工具用 `@tool(..., write=True)` 登记时只进了 `WRITE_TOOLS`，**没人记得同步这份手写列表**。
- **修复**：改为从注册表派生 —— `WRITE_INTENTS = set(WRITE_TOOLS)`，写意图不再手工维护。
- **预防**：**「安全清单」绝不允许手工维护**。凡是「新增 A 就必须同步改 B」的结构，一律改成从 A 派生 B；
  这条已写入项目约定。

### E-20 工具入参透传导致 `TypeError`（一次修得不彻底的教训）

- **现象**：店员问「今天有什么要处理的？」→ `query_todo() got an unexpected keyword argument 'appoint_date'`，
  会话直接中断。
- **根因**：意图识别抽出的槽位是**全局槽位字典**（含日期、宠物名等），执行时把非空值整体 `**args` 传给工具，
  而该工具并不接受这些参数。
- **修复**：`@tool` 登记时用 `inspect.signature` 记录处理函数的参数名，执行前按签名过滤。
- **我踩的第二个坑**：第一版用 `if not accepted or k in accepted` 判断，以为「空元组 = 没有参数信息」，
  但**空元组恰恰表示「这个工具不接受任何参数」** —— 短路放行，等于没修。
  必须区分 `None`（未知，不过滤）与 `()`（明确不接受参数）。
- **预防**：哨兵值要区分「未知」与「空」，别用一个 `if not x` 合并两种语义。

### E-21 工具异常回滚后访问过期 ORM 属性触发 `MissingGreenlet`

- **现象**：工具内业务校验失败 → `rollback()` → 紧接着写会话消息时抛 `MissingGreenlet`，**整个 SSE 流断掉**。
- **根因**：`rollback()` 会让该 Session 中所有 ORM 实例**属性过期**，之后任何属性访问都触发惰性加载；
  在纯 async 上下文里这会直接报错。
- **修复**：新增 `AgentRunner._recover_session()`，在 `except` 分支回滚后显式 `refresh` 会话对象（拿不到就按主键重查）。
- **预防**：**async ORM 里 `rollback()` 之后不要再碰旧对象**；要么重查，要么提前把用得到的字段取出来。

### E-22 冒烟测试用固定远期日期，重复运行会互相抢占时段

- **现象**：同一天连续跑两次冒烟，第二次报 `4090 时段已约满（容量 3）`，看起来像功能回归，其实是脏数据。
- **根因**：V5 段用例把日期写死为 `today + 280/281/282` 天，每次运行都往同一天同一时段塞单，
  容量（3）被前面几次跑满。
- **修复**：改为与主用例同源的随机远期偏移 `target + timedelta(days=400 + rnd.randint(0, 600))`，
  与其它用例的日期天然错开。**已实测同一库连续两次 94/94**。
- **预防**：**测试用例必须可重复执行**（无需清库）。凡是「写固定日期/固定唯一键」的用例，

## 2026-10-16 · V6（能力补全与工程加固）

### E-25 加了行锁依然超卖：MySQL 快照读把锁的效果抵消掉了（最有价值的一条）

- **现象**：为防超卖，在容量校验前对「日期 + 时段」加了 `SELECT ... FOR UPDATE` 行锁，
  结果 **6 个并发请求 6 单全部成功** —— 锁看起来完全没起作用。
- **根因**：MySQL 默认隔离级别是 **REPEATABLE READ**，容量校验用的是 `SELECT COUNT(*)`，
  属于**快照读**：即使外层已经用锁把并发串行化，后到的事务读到的仍是
  **自己事务开始时的旧快照**，看不到前一个事务刚提交的预约 → 校验通过 → 插入 → 超卖。
- **修复**：容量校验同样改成**当前读** —— `SELECT id ... FOR UPDATE`，取真实占用量并顺带锁住已有预约行。
  修复后 6 并发恰好 1 单成功、10 并发抢 2 名额恰好 2 单成功。
- **预防**：**「串行化」与「可见性」是两个独立问题**。只做前者（加锁）不做后者（当前读），
  在 REPEATABLE READ 下等于没防。凡「先查后写」的并发控制，查询语句必须用加锁读。
  另外：这类问题**只有真实并发测试能发现**，顺序调用的用例永远全绿。

### E-26 意图评测口径错误，得出虚低的准确率

- **现象**：首版评测脚本报「规则法准确率 52.4%」，宠主端 12 条样本**全部**被判为闲聊。
- **根因**：评测只调用了 `AgentRunner._operation_intent_by_rule()`（它**只负责店员/店长的运营意图**），
  没走 `_interpret_by_rule()` 这条完整链路 —— 宠主意图在后面的通用规则里，被整段跳过。
- **修复**：评测改调 `_interpret_by_rule()`；准确率随即变为 78.6%，补强规则后到 100%。
- **预防**：**评测要测「用户实际走的那条路」，而不是你以为的那条路。**
  测错层的评测比没有评测更危险 —— 它会让你去优化一个不存在的问题。

### E-27 规则关键词的「顺序」与「词表」同样重要（含一次自造回归）

- **现象 A**：「把流失预警天数从 90 改成 60」被判为「查流失预警」而不是「改配置」。
  因为写配置的判定要求文本含「配置/参数/设置」等名词，而口语化表达常常只有动词「改成」。
- **现象 B（我自己造出来的回归）**：把「配置」判定提前后，「最近谁改过门店配置」又被判成「查配置」，
  原本应命中「查审计日志」。
- **修复**：写操作（改成 / 调成 / 修改为 + 配置项关键词）**提到只读意图之前**；
  「门店配置只读」判定**移到店长专属意图之后**。另外补齐 3 处词表缺口
  （代客预约「给客户预约」、账号启停改为「账号 + 启停动词」组合判定、疑问句式优先于「预约」二字）。
- **预防**：规则法里**判定顺序就是优先级**。新增一条规则时，先问「它会不会抢走别人本来能命中的请求」，
  并把「我这条规则可能误伤什么」写进注释。

### E-28 `/tmp` 在 Git Bash 与 Windows Python 下不是同一个路径

- **现象**：`python -m pip freeze > /tmp/x.txt` 之后，脚本里 `Path("/tmp/x.txt")` 报文件不存在。
- **根因**：Git Bash 会把 `/tmp` 映射到用户临时目录，而 Windows 版 Python 把 `/tmp` 解析为
  **当前盘符根目录**下的 `\tmp`。两边指向不同位置。
- **修复**：跨工具传递中间文件时坚持用**相对路径**（或统一的 Windows 绝对路径）。
- **预防**：Windows 上不要让 shell 的原生路径语义跨进程传递，尤其是 `/` 开头的路径。

### E-34 把幂等键塞进核销码字段，`Data too long` 直接 500

- **现象**：用品下单报 `(1406, "Data too long for column 'pickup_code'")`，接口 500。
- **根因**：为省一个字段，我把幂等键写进了 `pickup_code`（`String(12)`），
  而幂等键形如 `smoke-1792220825-g-cart`（25 字符）—— **两个语义完全不同的东西挤在一个列里**。
- **修复**：拆成两个字段 —— `pickup_code`（8 位大写字母+数字，剔掉易混淆的 0/O/1/I，便于店员口述）
  与 `idempotent_key`（唯一索引，防重复提交）。
- **预防**：**一个字段只承担一个语义**。当你想「反正都是短字符串，放一起吧」，先问它俩的生命周期与唯一性是否一致。

### E-35 `SELECT ... FOR UPDATE` 仍然超卖：identity map 把当前读结果吃掉了（第二层陷阱）

- **现象**：V6 已经总结过「锁 + 当前读」，这次用品库存扣减照着写（`with_for_update()`），
  结果 **4 并发 4 单全部成功**，库存 1 卖了 4 件。
- **根因**：SQL 层面确实是当前读，但 ORM 层不是 —— 同一个 session 里此前已经加载过该 SKU
  （下单前的非锁定查询），SQLAlchemy 的 **identity map 会复用这个旧对象**，
  `FOR UPDATE` 返回的新行**不会刷新已存在的 ORM 实例**，于是 `sku.stock` 还是旧值 1。
- **修复**：取锁时必须加 `.execution_options(populate_existing=True)`，强制用数据库最新值覆盖 ORM 对象。
- **预防**：**「当前读」要贯穿到 ORM 对象层**：SQL 加锁 ≠ 内存里的对象是新的。
  凡「先读一次做校验、再锁行做写入」的路径，锁行那次读必须带 `populate_existing`；
  或者干脆不提前读，只锁行读一次。

### E-36 async 函数漏 `await`，接口返回一个协程对象

- **现象**：用品订单详情报 `TypeError: 'coroutine' object is not iterable`，且伴随
  `vars() argument must have __dict__ attribute`（FastAPI 序列化把协程当模型）。
- **根因**：`order_to_out()` 写成了 `async def`，调用处 `return order_to_out(...)` 忘了 `await`。
- **修复**：补 `await`。
- **预防**：纯拼装数据的序列化函数**不要声明成 async**（它不需要 IO）；只有确实要 await 时才 async。
  这类 bug 类型检查发现不了（返回类型是 `Coroutine`，被 `Any` 吞掉），只能靠冒烟覆盖到该接口。

### E-37 `await db.execute(count)` 之后直接 `int()` → TypeError

- **现象**：签发观看凭证时报 `int() argument must be ... not 'ChunkedIteratorResult'`。
- **根因**：`alive = (await db.execute(select(func.count())...) or 0)` —— `db.execute` 返回的是
  `Result`，`or 0` 对它无效（Result 是真值），`int(Result)` 自然报错。
- **修复**：计数一律用 `await db.scalar(...) or 0`。
- **预防**：**聚合查询用 `db.scalar()`，多行查询用 `db.execute()`**，两者别混用；
  这类错误只有真正走到该分支才暴露（这次是并发上限校验，正常路径不会触发）。

### E-42 `Settings.llm_available` 是只读 property，改不了也 patch 不了

### E-44 SSE 的逐字输出字段是 `delta`，不是 `content`

- **根因**：`answer` 事件的结构是 `{"type": "answer", "delta": "..."}`（逐字推送），
  脚本却按 `content` 取值，拼出来永远是空串。
- **修复**：改按 `delta` 聚合。
- **预防**：**断言前先看一眼事件的真实结构**（`grep '"type": "' app/agent/react.py` 五秒钟的事），
  别凭印象写字段名。

### E-45 `update_setting` 只写不提交，测试辅助漏 commit 造成「假通过」

- **现象**：实景用例里把观看时段改成 0–24 点、并发路数改成 1，结果完全没生效；
  更危险的是，这套「放开时段」的 fixture 一直静默无效 —— 用例只是因为**运行时恰好是白天**才通过。
- **根因**：`setting_service.update_setting` 末尾只有 `flush()`，**提交由调用方（路由）负责**；
  脚本里直接调用后没 `commit()`，会话关闭即回滚。
- **修复**：辅助函数补 `commit()`；同时在注释里写明「提交由调用方负责」。
- **预防**：**测试结果不能依赖运行时刻**。凡是「把某个时间窗/阈值放开」的装置，
  都要**断言它确实生效**（本轮的教训是：装置本身没生效，用例却全绿）。

### E-46 同事务里看不到另一连接刚插入的数据（测试里重演了 E-25）

- **现象**：体重档用例逐条造宠物、再逐条查回来，全部 `pet is None` → `'NoneType' has no attribute 'species'`。
- **根因**：MySQL REPEATABLE READ 下，用例先开了查询会话（事务快照固定），
  之后由**另一连接**插入的宠物在该事务里永远不可见。与 E-25（行锁 + 快照读）同源。
- **修复**：**先把数据全造完，再开查询会话**；或每次读完 `commit()` 重新开事务。
- **预防**：这条在服务层测试里会反复出现 ——
  「造数据」和「查数据」不要交错在同一个长事务里。

### E-47 业务规则写在路由里，服务层就无法测

- **现象**：补用品用例时发现 `ProductSku.unit_price_cents` 为空，前端「单位价」永远不显示。
- **根因**：单位价（分/kg）的计算**只写在路由** `POST /products` 里，
  服务层没有任何创建入口 —— 于是任何不经路由的调用（种子、脚本、测试、未来的 Agent 工具）都拿不到单位价。
- **修复**：抽出 `goods_service.upsert_product()`，单位价在服务层统一算，路由只做转发。
- **预防**：**路由只做三件事：解析入参、鉴权、调用服务**。业务计算一旦写进路由，
  就注定只有一条链路正确，其他入口全是隐性 bug。

### E-50 提前 return 规则结果，少了 `source` 字段把整个 SSE 打挂

### E-54 说「买成猫全价主粮（三文鱼）」，Agent 说找不到这个商品

### E-56 点「查看实时画面」，播放器里什么都没有

- **现象**：进入「宠物实景」能看到卡片，点「查看实时画面」后弹窗里一片空白，也没有任何提示。

- **预防**：**缓存 key 必须与业务身份对齐**。用「凭证」当缓存 key 看着安全，实则把

### E-58 向量检索的两个真问题：批量上限与维度锁死

- **现象 1**：重建索引时 embedding 返回 400 `batch size is invalid`。
  **根因**：百炼 embedding 单次最多 10 条文本。**修复**：按 10 条分批。
- **现象 2**：embedding 失败后自动降级到哈希向量，Chroma 抛
  `Collection expecting embedding with dimension of 1024, got 256`。
  **根因**：向量维度在创建 collection 时就定死了，换空间只 `delete(where={})` 不重建 collection 无效。
  **修复**：空间变化时 `delete_collection` + 重建，并把 `space`（含 `|chunk-v1`）写侧车文件。
- **现象 3**：问「耳后小面积试洗规则」，最相关的那篇排第 3，被「病灶部位洗护手法」压过。
  **根因**：整篇长文档做一个向量，查询只命中其中一节时相似度被整篇其它内容稀释。
  **修复**：按 `## ` 小节切块（17 条知识 → 36 个 chunk），命中后只回该节正文。
  修完 top-1 命中率从 3/6 提升到 6/6。
- **预防**：**"基础 RAG" 也要分块**。只要单篇超过两三百字，整篇嵌入的召回就会被稀释；
  另外向量库的「维度 / 空间」属于建库参数，换 embedding 必须整库重建，不能只清数据。

## 2026-10-20 · V8.4 / V8.4.1（RAG 重写与兜底）

### E-59 知识检索一出错，整条回复就变成「系统开小差」

- **现象**：问「常见致敏成分的清单」，工具确实被调起了，但整条回复是一句红色错误
  「抱歉，系统开小差了」。用户视角：RAG 根本没实现。
- **根因**：`search_knowledge` 内部任何异常（向量库未建、embedding 限额、rerank 超时）
  都会冒泡到 Agent 的统一异常处理 —— **一个可降级的只读能力，把整条消息拖死**。
- **修复**：工具内部 `try/except` 包住整条检索链路，失败后退回 `knowledge_service.search_by_text`
  （纯标签打分），最差也只回「通用规范」，不再报错。
- **同期另一个坑（详见 `docs/08` 5.2）**：`DashScopeEmbedding` 默认 `embed_batch_size=100`，
  而百炼单次最多 10 条，**超了不报错、返回全 None 向量** —— 表现为「索引建了但什么都搜不到」。
  已固定 `embed_batch_size=10`。
- **预防**：**可降级能力必须在能力内部兜底**。RAG/检索这类「锦上添花」的能力，
  异常绝不能冒到统一处理层；宁可给一个次优答案，也不要让用户觉得功能没做。

### E-60 冒烟断言在「固定分页窗口」里数条数，数据攒够就假失败

- **现象**：冒烟第 30 节「疫苗临期提醒真实发出站内信」偶发 FAIL，日志显示 `2 -> 2`，
  而任务明明返回 `sent: 1`，库里也确实新增了一条提醒。
- **根因**：断言取「消息列表第 1 页 50 条」再数其中 `vaccine_remind` 的条数。列表按 id 倒序，

- **验证**：修复后连续两轮 239/239（新增 1 条断言）。
- **预防**：**断言不要用「第 1 页里有多少条」这种窗口计数**。凡是「执行后新增了什么」，

### E-63「结束观看」点了没反应，弹窗卡在「正在申请观看凭证…」

- **预防**：**带默认布尔参数的函数不要直接绑到 `@click`**。Vue 必然传事件对象，
  任何 `if (!flag)` 都会静默失效 —— 这类 bug 不报错、不抛异常，只表现为「按钮没用」。

### E-65「不管问什么，检索到的都是同一批内容」

- **现象**：连问「可复用的安抚手法」「什么时候改用免水洗」，回答都是

- **预防**：**检索类系统的「索引新鲜度」必须可判定**。把「建索引时的知识量」写进索引

### E-66 宠主端实景「一顿一顿」的

- **现象**：画面能看，但明显卡顿、延迟高。

  （有寄养单引用时 409，提示改用「维护中」停用）。
- **预防**：**upsert 语义要显式**。「按业务键定位，找不到就插入」在新增场景里是危险的默认行为。

## 2026-10-21 · V8.4.9（AI 口语选房 + 实景选宠跳转 + 提前接回归宠主）

### E-73 AI 寄养「找不到房间」：用户说不出房号

- **现象**：宠主在 AI 里说「给我家狗订个寄养」，助手要么回「找不到房间」，
  要么反问一串房号，用户根本不知道该说 A101 还是 V905。
- **根因**：下单工具只认 `room_id` / `room_no`，而用户表达的是**房型**（标准 / 花园 / VIP）
  或干脆不表达；服务层没有「从自然语言到房舍」的解析，只能把选择权甩回给用户。
- **修复**：`boarding_service.resolve_room()` 三级解析 —— 房号精确命中 → 房型别名归一
  （`ROOM_TYPE_ALIASES`：标准房 / 单间 / 花园房 / 阳光房 / VIP / 套房 …）→ 在
  「体重与物种都装得下 + 所选日期可订」的候选里取最便宜一间。三级共用同一套可订校验。
- **顺带**：解析不出房型时，回答里把**可选房型与起价**列出来（「标准单间 ¥60/晚起」），
  用户照着念一遍就能下单，而不是面对一句「请提供房号」。

### E-74 实景做成了「聊天内弹窗播放」，方向错了

- **现象**：我按「直接打开画面」的字面意思，在聊天页内做了 `CameraPlayerDialog` 组件，
  用户现场纠正：**要跳到宠物实景页面再打开对应画面**。
- **根因**：把「打开画面」理解成了 UI 载体（弹窗），而用户要的是「去该去的功能页」——
  实景页有完整的观看凭证、时长留痕与结束观看，聊天里塞一个播放器等于另起一套。
- **修复**：删掉播放弹窗，改成下发 `navigate /user/camera?order_id=<id>`；
  宠主端 `Camera.vue` 在 `onMounted` 读 `?order_id=` 自动申请凭证开播。
- **预防**：**「打开某个功能」优先理解为导航**，别在对话里复刻功能页；
  功能页独有的状态机与留痕，聊天内重做一份必然不一致。

### E-75 演示单落在没装摄像头的宠舍，实景看着像坏了

- **现象**：清空测试数据后重新造的在住演示单在 V903，宠主端实景显示
  「该宠舍尚未安装摄像头」——演示时这一块直接判死刑。
- **根因**：`seed_demo_boarding.py` 只在**已存在设备**时补心跳，没有设备就不管了；
  而能被订到的那间房恰好没摄像头是常态（房态天天变，光靠「优先选有摄像头的房」保证不了）。
- **修复**：抽出 `ensure_camera()` —— 没有设备就装一台并置在线。演示数据的一部分，
  与业务代码无关。同一轮还发现 `reset_rooms.py` 删房舍时不删挂在上面的摄像头，
  留下「房舍已不存在」的孤儿设备（店员端看着像装了，点进去什么都推不了）→
  改为每次运行都清理孤儿（有观看留痕的保留对账）。
- **预防**：**新增业务表要同步进清理 / 重建脚本**——本轮 `cleanup_business.py`
  的寄养分组就漏了 `boarding_early_pickup`（又是「新增 A 必须同步改 B」）。

### E-76 浏览器用例断言了模型措辞，被历史数据打成假失败

- **现象**：`verify-spa.mjs` 里「店员收到待办类回复」用 `/待办|待确认|待复核|今日/` 匹配，
  某次跑挂了——模型回复里是一串宠物名（并发犬 / 契约测试犬），一个关键词都没有。
- **根因**：断言测的是**模型措辞**，不是「店员 AI 能用」；措辞随库里的数据变来变去。
- **修复**：断言改成「有实质回复 + 说到业务对象」（`预约|单|今天|没有|…`），
  把「模型怎么说」还给模型。

## 2026-10-24 · V8.5.0（店员/店长 RAG 知识库管理）

### E-77 上传文档已经切块，建索引时又被默认规则二次切碎

- **风险**：店长选择「按标题 / 1000 字 / 重叠 100」，若仍统一经过 `SentenceSplitter(500/50)`，
  界面显示的切块与 Chroma 实际检索块不一致，页码和段落追溯也会失真。
- **修复**：`knowledge_chunk` 作为上传文档切块的唯一事实来源；建索引时上传块直接构造 `TextNode`，
  只有内置长条目继续走默认 SentenceSplitter。索引元数据同时区分 `entry_id` 与 `chunk_id`。

### E-78 入库任务先重建索引、后把文档标完成，导致新块永远没进索引

- **根因**：索引查询只读取 `knowledge_document.status=completed`，第一版在 reindex 完成后才设 completed，
  因而重建时看不到刚写入的块。
- **修复**：切块与元数据先事务提交为 completed，再串行重建索引；重建失败由统一异常处理改回 failed，
  保留错误原因，店长可手工重建。

### E-79 目录类配置写成相对路径，cwd 一变就在别处另建一份 data/

- **现象**：`CHROMA_DIR="data/chroma"`、`KB_UPLOAD_DIR="data/knowledge_uploads"` 都是相对路径，
  `Path(...).resolve()` 按**进程 cwd** 解析。从 `backend/` 启服务落在 `backend/data/`，
  从项目根跑脚本却在项目根又建一份 `data/` —— 两个向量库、两个上传目录同时存在，
  检索与「删除时回收磁盘文件」都可能对不上。
- **修复**：`app/config.py` 以本文件位置为锚点（`_BACKEND_DIR`），新增 `model_validator`
  把目录配置统一锚定到 `backend/`；绝对路径配置原样保留，不影响自定义部署。
- **教训**：凡是「磁盘目录」型配置都不要依赖 cwd，锚定到代码位置才不会随启动方式漂移。

### E-80 浏览器用例固定 sleep 等 LLM，长流程后取到空回复

- **现象**：店员发「我今天有什么要处理的？」后 `sleep(9000)` 再取气泡文本；整轮跑到第 4 节时
  LLM 主链偶发 10s+ 才出首字，取到空串 → 「店员收到运营类回复」失败。单独重跑却又通过，
  是典型的**时序型假失败**。
- **修复**：新增 `waitAssistantAnswer()` 轮询等待助手气泡出现实质内容（上限 35s），
  拿到后再等 1.5s 避免只抓到半句；固定 sleep 只保留在 DOM 渲染等待上。
