# 简历 · PawPilot 的 Agent 部分（直白版）

## 正文

这个项目是一个宠物洗护门店的管理系统，我在里面做了一套多 Agent 的 AI 助手。它不是那种只会聊天的
机器人，是真的能替用户下单、查订单、跳页面的。整套系统能自己跑起来：预约、寄养、买用品、
看宠物实景、问养宠知识，五块业务全接在里面。

技术栈很常规。后端 FastAPI，数据库 MySQL 8，前端 Vue3 + TypeScript + Element Plus。大模型用
阿里云百炼：主模型 qwen3.7-max，挂了自动换 glm-5.1，两个都不可用就退到规则引擎；文本转向量用
text-embedding-v4，检索结果精排用 text-rerank。模型名全在配置里，代码里不写死。

Agent 这块我自己设计了九个角色：一个路由 Agent 在入口判意图、派活、最后合并结果，底下挂了
健康问诊、饲养营养、行为训练、用品导购、宠物档案、门店业务、经营分析七个领域 Agent，另有一个合规风控
Agent 横着切——每轮回答都过它一遍，识别到急症、处方药、偏方就直接改写给用户看的内容。
拆开的原因很实际：健康问诊的红线是"不诊断、不开处方"，用品导购要贴着库存和价格说话，
把这些塞进同一个提示词里，规则会被稀释。拆开以后每个 Agent 只带自己那套领域提示和工具子集，
规则不打架。

但这九个 Agent 不是九个进程、也不是九个模型，它们共用同一个 ReAct 执行器和同一张工具表，
本质上是"一套执行内核 + 八份领域配置"。我也没引 CrewAI、AutoGen 这类多 Agent 框架——
那些框架让 Agent 之间自由对话协商，流程就不可预测了，出了事也查不清是哪个 Agent 决定的。
我的编排是写死的：用户说"我家金毛拉稀，吃什么粮"，路由先派健康问诊判风险，把结论当上下文
传给营养 Agent 出饮食方案，再让风控过一遍，最后合成一条回复。有依赖就串行，没依赖才并行，
子 Agent 之间不直接说话。

流程正确性不靠 Agent。预约、寄养这些业务我画成了显式状态图：每个节点是一个业务状态，
每条边是一次状态转移，中间用状态机卡着，不许乱跳。Agent 只负责"理解用户要什么、该调哪个工具"，
状态合不合法由后端的迁移表说了算。整个过程用 SSE 一点点推给前端，一共 14 类事件：思考、意图、
调了什么工具、工具返回什么、要不要用户确认、跳到哪个页面、给了哪些选项、为什么看不了、
检索到哪些片段、回答正文。前端没用 EventSource，是 fetch 加 ReadableStream 自己解析，
按事件类型分块渲染，所以用户能看到 AI 在想什么，而不是干等一个转圈。

工具写了 30 个，其中 13 个是会改数据的。三个端看到的工具不一样：宠主 13 个，店员 11 个，
店长 11 个。工具用 @tool 装饰器注册，注册的时候用 inspect 把参数名记下来，模型给的参数里要是有
不相干的字段，执行前直接过滤掉，不然会 TypeError。权限查两道：装饰器上声明允许哪些角色，
运行时再按当前端能用的工具收一遍。端与端的差别不只是工具——哪些 Agent 能激活也不一样，
比如营养和行为训练只对宠主完整开放，店员只能查方案，店长压根没有；反过来经营分析和知识库治理
只有店长有。

会改数据的操作，我不让模型直接执行。全部走同一条路：先做只读预检（比如疫苗有没有过期、
房间还订不订得到），过了让用户点确认，确认后才进业务服务层，然后状态机、事务、审计日志。
哪些工具算写操作不是我手写清单，是从工具注册表自动算出来的（WRITE_INTENTS = set(WRITE_TOOLS)），
以后加一个写工具不用记得再去改闸门。表单提交和 AI 下单调的是同一个 Service 方法、
带同一个幂等键，所以不会出现"表单下的单和 AI 下的单不一样"。

意图识别做了两条路：先用规则匹配，规则认不出再问模型；模型挂了就只用规则，业务照跑。模型有时
会判错，比如把"看看宠物状态"判成查预约，所以模型的判断还要再过一遍角色权限，越权就退回规则的
结果；规则已经确定是写操作的时候，也不许模型把它改成闲聊——不然用户说了半天，系统当成寒暄，
操作静默丢了，比报错更难查。我写了 45 条测试问题把三个端都覆盖到，规则法和模型法都是
100% 命中，模型挂了准确率不掉。

知识库用 ChromaDB 加 LlamaIndex，分了六个逻辑分片：疾病、营养膳食、饲养管理、行为心理、
用品商品、门店私有（套餐、价格、到店须知、客户病历），检索时按目标 Agent 限定分片，候选集小了
命中更准。切块切了两遍：先按 Markdown 的二级标题切成小节，再在每个小节里用 SentenceSplitter 切，
chunk_size 500、overlap 50。这么切是因为只按字数切会出现"文档找对了、段落答错了"。embedding
有四级兜底：text-embedding-v4 → 备选模型 → 本地哈希 → 标签打分，一批最多 10 条（百炼的限制）。
向量维度在建 collection 的时候就定死了，换模型只能重建；索引里记着知识条目数，每次检索前跟
数据库比一下，对不上就自动重建，不靠"记得手动跑脚本"。

**RAG 只有对话一个入口，没有单独的搜索页。** 检索是 Agent 的一个工具（search_knowledge），
Agent 判断这轮需要专业知识才调。知识库管理页只做文档治理——上传、切块、看任务状态、删除、
重建索引，就这些，没有搜索框。理由是检索的价值是支撑回答，脱离回答单独搜一段文本，用户拿不到
结论，还多一个要维护的入口。检索分三段优化：检索前把口语归一、查索引新不新；检索中向量和关键词
标签一起召回；检索后 rerank 精排，卡相关度（rerank 0.45、向量 0.30），全都不达标也至少返回
分最高的那条。检索到的片段不只用来生成答案，还会单独发给前端折叠展示，用户能点开看是哪篇文档的
哪个小节，答案有出处，不是模型编的。

测试方面：服务层单测 106 个，覆盖率 82.05%；接口冒烟 261 条断言；浏览器端到端 123 项；
另外做了 22 项故障注入，把模型、embedding、向量库分别弄挂，业务都不中断。

## 关于 LangChain / LangGraph

项目确实没用这两个框架，上面写的是"自己实现 ReAct 循环 + 状态图编排"。面试问起来，
这个答案比直接说"用了 LangGraph"更有料——你能讲清楚为什么不用：一是写操作的责任链必须收在
业务服务层，交给框架自主编排就把这条链拆散了；二是多 Agent 那块，框架的默认玩法是让 Agent
互相协商，而门店业务需要的是可枚举的串行编排，协商反而制造不确定性。

如果想让这两个词以"用过"的形式出现在简历上，可以真补：一是加一个 LangChain 的对比实验模块，
简历写"对比验证后选择自研"，半天能做完；二是用 LangGraph 重写寄养订单状态机（状态少、转移
清晰，最适合迁移），简历写"基于 LangGraph 实现寄养状态图，与自研 Agent 编排协同"，一两天。
需要的话直接说，我来做。
